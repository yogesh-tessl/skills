## PLC vs DCS vs PAC — 怎麼選？

這是系統整合專案最常被問的問題之一。答案不是「哪個比較好」，而是「你的場景適合哪個」。

### 決策矩陣

| 判斷維度 | 偏向 PLC | 偏向 DCS | 偏向 PAC |
|---------|---------|---------|---------|
| 製程類型 | 離散製造（Discrete） | 連續/批次製程（Continuous/Batch） | 混合製程 |
| 類比迴路數 | < 100 個 | > 500 個 | 100-500 個 |
| 控制速度需求 | 毫秒級（快速離散邏輯） | 秒級（穩態調節） | 介於兩者之間 |
| 系統規模 | 單機或小產線 | 整廠或大型裝置 | 中型產線 |
| 安全完整性等級（SIL） | SIL 1-2（搭配安全 PLC） | SIL 2-3（內建安全系統） | SIL 1-3 |
| 操作員介面需求 | 簡單 HMI | 大型中控室、多層畫面 | 中等 |
| 標準批次控制（ISA-88） | 需另外實作 | 通常內建 | 部分內建 |
| 生命週期成本 | 硬體便宜，工程費用中等 | 硬體貴，但大型專案整體效率高 | 介於兩者 |
| 供應商鎖定程度 | 中（各家程式不完全相容） | 高（遷移成本很高） | 中 |
| 典型產業 | 汽車、包裝、半導體設備 | 石化、煉油、製藥、發電 | 水處理、食品、建材 |

### 情境判斷（直接用這個）

| 你的情境 | 選擇 | 理由 |
|---------|------|------|
| 設計一台包裝機 | PLC | 以離散邏輯和運動控制為主，不需要複雜的製程調節 |
| 煉油廠新建一套蒸餾裝置 | DCS | 大量類比迴路、嚴格安全要求、需要完整的批次管理和操作員介面 |
| 污水處理廠升級自動化 | PAC 或小型 DCS | 有數十個類比迴路（pH、溶氧、流量），但規模不到大型 DCS 的門檻 |
| 半導體設備控制器 | PLC + 工業電腦 | 快速離散邏輯 + 複雜配方管理（配方部分通常在工業電腦上實作） |
| 既有 PLC 系統需要加類比控制 | 加 PID 模組，不必換 DCS | 除非類比迴路數量暴增到上百個，否則 PLC 的 PID 功能夠用 |
| 全新建廠，規模不確定 | 先評估三年後的規模再決定 | 現在省的平台費用，三年後可能因為規模不適配而加倍還回來 |

### PAC 到底是什麼？

PAC（Programmable Automation Controller）是 PLC 和 DCS 的混合體。簡單說：

- 有 PLC 的高速離散控制能力
- 有 DCS 的進階製程控制功能（PID、批次、資料記錄）
- 通常跑在更開放的軟體平台上（例如 Windows/Linux 作業系統）

**誠實評價**：PAC 這個詞常被行銷部門用來包裝「進階 PLC」。選型時不要被名稱迷惑，回到實際功能需求去比較。

## IEC 61131-3 五大語言

IEC 61131-3 定義了五種程式語言（嚴格說是三種語言加兩種圖形方法）。選哪一種不只是技術問題，更是人力市場和產業慣例的問題。

### 語言對照表

| 語言 | 中文 | 類比 | 強項 | 弱項 |
|------|------|------|------|------|
| **LD** | 階梯圖（Ladder Diagram） | 像電氣接線圖 | 簡單的開關邏輯、電氣工程師容易上手 | 複雜演算法寫起來冗長、難以維護 |
| **FBD** | 功能方塊圖（Function Block Diagram） | 像電路方塊圖 | 類比控制、PID 迴路配置、信號處理 | 大量邏輯分支時畫面雜亂 |
| **ST** | 結構化文字（Structured Text） | 像 Pascal/Python | 複雜演算法、資料處理、數學運算 | 電氣工程師不習慣、除錯不如圖形直覺 |
| **IL** | 指令列表（Instruction List） | 像組合語言 | 無——已被 IEC 標準標記為棄用 | 可讀性極差、無人願意維護 |
| **SFC** | 順序功能圖（Sequential Function Chart） | 像流程圖 | 順序控制、步進流程、批次控制 | 不適合純邏輯或純類比控制 |

> ⚠️ IL（指令列表）已在 IEC 61131-3 第三版中被標記為棄用（Deprecated）。新專案不應該使用 IL。如果遇到舊系統是 IL 寫的，翻新時應轉換為 ST。

### 各產業的偏好與原因

| 產業 | 主要語言 | 為什麼 |
|------|---------|--------|
| 汽車製造 | ST + LD | ST 處理複雜的工藝邏輯（焊接參數計算、品質追蹤），LD 處理基本安全聯鎖。汽車業人才庫偏好 ST |
| 水處理 | FBD + LD | 大量 PID 迴路適合 FBD 圖形化配置，簡單的泵浦開關用 LD。現場維護人員偏好圖形化介面 |
| 包裝機械 | SFC + LD | 包裝流程天然是步進的（進料→填充→封口→出料），SFC 完美對應。安全聯鎖用 LD |
| 製藥 | SFC + ST | ISA-88 批次控制的階段（Phase）用 SFC 實作，複雜的配方計算用 ST。製藥法規要求可追溯性，ST 的版本管理比圖形語言容易 |
| 石化 | FBD（DCS 內建） | DCS 平台通常以 FBD 為主要介面，類比控制配置非常直覺 |
| 半導體設備 | ST + C/C++ | 設備控制器越來越複雜，ST 或直接用高階語言。PLC 只負責基本安全和 I/O |
| 食品飲料 | LD + SFC | LD 是產業主流（人才最多），SFC 處理清洗（CIP）等步進流程 |

### 混合使用的最佳實務

一個專案內混用多種語言是正常的。建議的分工：

- **SFC**：管控整體流程步驟和批次順序
- **ST**：寫在 SFC 的動作（Action）裡處理計算邏輯
- **FBD**：PID 迴路和訊號處理
- **LD**：安全聯鎖和基本數位邏輯（這部分讓電氣工程師能維護）

**核心原則**：選語言要考慮「誰來維護」。如果你的客戶現場只有電氣背景的維護人員，全寫 ST 他們會完全無法除錯。反過來，如果你的控制邏輯需要大量數學運算，硬用 LD 寫會成為維護災難。

## IEC 61499 分散式控制

IEC 61499 是 61131-3 的「下一代」標準，設計用於分散式和事件驅動的控制系統。

### 和 IEC 61131-3 的根本差異

| 面向 | IEC 61131-3 | IEC 61499 |
|------|-------------|-----------|
| 執行模型 | 掃描式（Scan-Based）：固定週期掃描所有程式 | 事件驅動（Event-Driven）：有事件才執行 |
| 部署單位 | 程式綁定在單一 PLC 上 | 功能方塊可跨多個裝置分散部署 |
| 可移植性 | 各家 PLC 平台之間不完全相容 | 設計目標是跨平台可移植（但現實差距仍大） |
| 適合場景 | 集中式控制、固定拓撲 | 分散式系統、可重組產線、物聯網邊緣 |

### 目前的採用狀況（誠實版）

**現實是**：IEC 61499 在學術界受到高度關注，但在工業現場的實際採用仍然有限。原因：

1. **工具鏈不成熟**：支援 61499 的開發環境遠少於 61131-3
2. **人才稀缺**：幾乎沒有工程師有 61499 的實戰經驗
3. **既有投資**：客戶已經在 61131-3 平台上投入大量資產（程式、培訓、備品）
4. **供應商支援**：主流 PLC 品牌對 61499 的支援仍是「有支援但不是主推」

### 什麼時候值得考慮 61499？

- 設計模組化、可重組的智慧產線（Industry 4.0 概念驗證）
- 需要在多個邊緣控制器之間分散部署控制邏輯
- 研究專案或長期技術布局

**大部分實務專案**：繼續用 IEC 61131-3，這不是保守，是務實。

## SCADA 架構設計

SCADA（Supervisory Control and Data Acquisition，監控與資料擷取）是操作員看到的那一層。設計好壞直接影響操作效率和事故應變能力。

### 架構選型

| 架構 | 特性 | 適用場景 | 風險 |
|------|------|---------|------|
| 傳統集中式 | 單一伺服器 + 專用客戶端 | 單一廠區、中小規模 | 單點故障、擴充受限 |
| 冗餘集中式 | 主備伺服器 + 自動切換 | 需要高可用性的中型廠 | 仍有地理限制 |
| 分散式（多伺服器） | 多個 SCADA 伺服器協同 | 大型廠區或多廠管理 | 資料同步、組態管理複雜 |
| 雲原生 / 網頁式 | 瀏覽器存取、容器化部署 | 新建專案、遠端監控需求高 | OT 資安顧慮、即時性限制 |

### 現代趨勢：網頁式 SCADA

越來越多 SCADA 平台支援純網頁介面（HTML5），取代傳統的專用客戶端軟體。

**優點**：
- 不需安裝客戶端軟體，降低維護成本
- 跨平台存取（桌機、平板、手機）
- 更容易整合到企業入口網站

**但要注意**：
- 即時性不如原生客戶端——網頁更新頻率受限於瀏覽器和網路
- 需要認真處理 OT 資安——網頁介面意味著更多攻擊面
- 操作關鍵畫面（緊急操作）仍建議保留原生客戶端或專用操作站

### 歷史資料庫（Historian）整合

SCADA 和歷史資料庫（Historian）是不同的系統，但必須緊密整合：

- **SCADA 負責即時**：顯示當前狀態、操作控制
- **Historian 負責歷史**：長期趨勢、效能分析、合規報表

**設計要點**：
- 不要用 SCADA 的內建記錄功能取代專業 Historian——SCADA 的儲存效率和查詢效能不是為長期大量數據設計的
- Historian 的數據壓縮演算法（例如旋轉門壓縮, Swinging Door Compression）要理解並正確設定——壓縮比設太高會丟失重要的暫態行為
- 命名規範（Tag Naming Convention）在專案早期就要定好，後期改名的成本極高

> HMI 畫面設計原則（ISA-101 高效能圖形）和警報管理（ISA-18.2），參見 [devops-hmi.md](devops-hmi.md)。

## 運動控制

運動控制（Motion Control）是機械自動化的核心技術——精準控制馬達的位置、速度、扭矩。

### 伺服系統選型流程

選型順序很重要，不能反過來做：

```
① 負載分析        → ② 齒輪比設計     → ③ 扭矩/速度曲線
  （負載慣量、      （慣量匹配、        （連續扭矩、
    摩擦力、          減速比）           峰值扭矩、
    外力）                               最高轉速）
                                              │
④ 馬達選型        ← ⑤ 驅動器選型     ← ⑥ 通訊介面
  （伺服馬達型號、   （電流容量、        （EtherCAT、
    編碼器解析度）     功能需求）         PROFINET、
                                          Mechatrolink）
```

#### 第一步：負載慣量計算

| 負載類型 | 慣量公式（白話） | 常見陷阱 |
|---------|----------------|---------|
| 直接驅動（旋轉負載） | 就是負載本身的轉動慣量 | 別忘了聯軸器和編碼器的慣量 |
| 滾珠螺桿（線性轉旋轉） | 線性質量換算成等效旋轉慣量 | 螺桿本身的慣量容易被忽略 |
| 皮帶/齒輪傳動 | 透過傳動比折算到馬達軸 | 傳動效率不是 100%，通常 85-95% |
| 凸輪機構 | 隨角度變化的等效慣量 | 最大慣量出現的位置才是設計點 |

#### 慣量匹配原則

馬達慣量和負載慣量的比值是系統穩定性的關鍵：

| 慣量比（負載/馬達） | 評價 | 適用場景 |
|-------------------|------|---------|
| 1:1 ~ 3:1 | 理想 | 高精度定位、快速往復運動 |
| 3:1 ~ 5:1 | 可接受 | 一般搬運、輸送 |
| 5:1 ~ 10:1 | 需要降速比或選大馬達 | 須加減速機 |
| > 10:1 | 不建議直接驅動 | 系統難以穩定，必須加減速機 |

> 超出慣量比建議值不是「一定不行」，而是調參（Tuning）難度急劇上升，系統對外部擾動的穩健性下降。

### 電子凸輪（Electronic Cam）

電子凸輪用軟體取代機械凸輪，實現主從軸之間的非線性運動關係。

**典型應用**：包裝機的封切動作、印刷機的套色對位、瓶裝線的灌裝對位。

**設計要點**：
- 凸輪曲線的連續性決定運動品質——至少要三階連續（位置、速度、加速度都連續），否則會有機械衝擊
- 常用曲線類型：修正正弦（Modified Sine）、修正梯形（Modified Trapezoid）、五次多項式（5th Order Polynomial）
- 凸輪表（Cam Table）的解析度要夠——點數太少會造成速度波動

### 多軸同步控制

多軸同步的核心是「所有軸在同一個時間基準下動作」。

| 同步等級 | 精度 | 實現方式 | 應用 |
|---------|------|---------|------|
| 粗同步 | ±1ms | 控制器內部任務排程 | 簡單搬運、多軸獨立但需協調 |
| 精同步 | ±1μs | 分散式時鐘同步（DC, Distributed Clock） | 電子齒輪、電子凸輪、插補運動 |
| 超精同步 | <100ns | 專用運動控制匯流排 + 硬體時間戳 | 高速印刷、雷射加工 |

**現場匯流排選擇**：EtherCAT 是運動控制的首選協定——週期時間短（250μs 以下可達）、抖動小（<1μs）、支援分散式時鐘。PROFINET IRT（Isochronous Real-Time）也可以，但生態系不如 EtherCAT 豐富。

> 現場匯流排的詳細比較，參見 [protocols-integration.md](protocols-integration.md)。

### PLCopen 運動控制功能方塊

PLCopen 定義了一套標準化的運動控制功能方塊（Function Block），讓程式可以在不同品牌的控制器之間移植。

| 功能方塊類別 | 常用方塊 | 功能 |
|------------|---------|------|
| 單軸控制 | MC_Power, MC_MoveAbsolute, MC_MoveRelative, MC_MoveVelocity | 基本的上電、定位、速度控制 |
| 多軸協調 | MC_CamIn, MC_GearIn, MC_MoveLinearAbsolute | 電子凸輪、電子齒輪、線性插補 |
| 狀態管理 | MC_ReadStatus, MC_ReadActualPosition, MC_Reset | 軸狀態監控和錯誤重置 |
| 進階 | MC_TouchProbe, MC_AbortTrigger | 高速觸發（用於量測和定位） |

## 機器人整合

### 工業機器人 vs 協作機器人——不只是「有沒有圍籬」

| 面向 | 工業機器人（ISO 10218） | 協作機器人（ISO/TS 15066） |
|------|----------------------|--------------------------|
| 速度 | 快（典型 1-2 m/s 以上） | 受限（協作模式下通常 < 250 mm/s） |
| 負載 | 重（3-1300 kg） | 輕（通常 3-25 kg） |
| 安全措施 | 實體圍籬 + 安全光柵 + 安全門 | 力覺限制 + 速度限制 + 安全設計 |
| 部署成本 | 機器人便宜，但周邊（圍籬、安全系統）貴 | 機器人較貴，但周邊簡化 |
| 適用場景 | 高速高精度、惡劣環境、大負載 | 人機共存、彈性產線、輕負載 |
| 常見誤解 | — | **「協作機器人天生安全」是危險的誤解** |

### 協作機器人的安全評估——不能跳過

> ⚠️ 協作機器人**不是**「拆了圍籬就可以用」。ISO/TS 15066 明確要求進行風險評估，並根據評估結果設定力量和速度限制。

ISO/TS 15066 定義了四種協作操作模式：

| 模式 | 機制 | 適用場景 | 限制 |
|------|------|---------|------|
| 安全額定監控停止（Safety-Rated Monitored Stop） | 人進入協作區域時機器人停止 | 偶爾需要人工介入的工站 | 停止 = 產能損失 |
| 手動導引（Hand Guiding） | 操作員手動帶領機器人運動 | 教導、彈性路徑 | 需要力覺感測器 |
| 速度與距離監控（Speed and Separation Monitoring） | 根據人機距離動態調整速度 | 人機頻繁共存的工站 | 需要安全感測系統（光柵、雷達） |
| 功率與力量限制（Power and Force Limiting） | 碰撞力量限制在安全值以下 | 緊密人機互動 | 速度和負載受限 |

**最重要的一件事**：力量限制的安全值取決於碰撞的身體部位——手指能承受的力（140N）和胸部能承受的力（210N）差很多。工具端的形狀也很關鍵——尖銳工具的容許力量遠低於鈍面接觸。

### 機器人與 PLC 的通訊

| 通訊方式 | 特性 | 適用場景 |
|---------|------|---------|
| 數位 I/O | 簡單可靠，但資訊量低 | 基本的啟動/停止/完成信號 |
| 現場匯流排（EtherNet/IP, PROFINET） | 資料量大，可傳送座標和狀態 | 需要交換程式編號、位置資料 |
| 專用機器人介面（Robot API） | 最完整的控制和監控能力 | 進階應用——路徑即時修正、力覺控制 |

**實務建議**：不要過度依賴數位 I/O——看似簡單，但當交握信號（Handshake）複雜到需要十幾個 I/O 點時，除錯會非常痛苦。中型以上的整合案建議用現場匯流排。

### 機器人工作單元（Cell）設計

| 設計面向 | 要點 |
|---------|------|
| 動線規劃 | 物料進出路徑不能和人員通道交叉 |
| 夾治具設計 | 夾治具失效（斷氣、斷電）時工件不能掉落——這是安全需求 |
| 工具端點校正（TCP） | 機器人的「手指尖」位置必須精確——偏差 1mm 在重複精度 ±0.05mm 的機器人上完全抵銷了精度優勢 |
| 坐標系定義 | 工件座標系（Work Frame）要基於可靠的機械定位基準，不要依賴視覺每次重新定位 |
| 碰撞防護 | 奇異點（Singularity）附近的路徑規劃要特別注意——機器人可能突然大幅加速 |

> 機器人安全標準的詳細說明，參見 [safety-security.md](safety-security.md)。

## 機器視覺

### 自動光學檢測 vs 線上檢測——釐清需求

| 類型 | 目的 | 速度要求 | 精度要求 | 部署位置 |
|------|------|---------|---------|---------|
| 自動光學檢測（AOI） | 品質判定（良/不良） | 配合產線節拍 | 中到高 | 產線上特定檢測站 |
| 線上量測（Inline Metrology） | 尺寸量測、位置量測 | 即時 | 高到極高 | 製程工站旁 |
| 離線檢測（Offline Inspection） | 深度品質分析 | 無即時要求 | 最高 | 實驗室或獨立檢測區 |

### 照明-幾何-光學三角（最重要的設計原則）

> 機器視覺的第一法則：**照明決定成敗**。一套一萬元的照明搭配五萬元的相機，效果通常優於一萬元的照明搭配二十萬元的相機。

| 照明類型 | 原理 | 適用場景 | 注意事項 |
|---------|------|---------|---------|
| 環形光（Ring Light） | 均勻正面打光 | 平面檢測、顏色辨識 | 反光表面會出現亮斑 |
| 背光（Backlight） | 從背面打光，看輪廓 | 外形量測、有無檢測 | 只能看輪廓，看不到表面特徵 |
| 同軸光（Coaxial Light） | 光線和鏡頭同軸 | 鏡面或高反光表面 | 成本較高，有效距離受限 |
| 條形光/側光（Bar/Side Light） | 低角度側面打光 | 表面缺陷（刮痕、凹陷） | 光線方向性強，可能漏掉某些角度的缺陷 |
| 穹頂光（Dome Light） | 散射均勻光 | 曲面、多角度反光物件 | 體積大、視野受限 |
| 結構光（Structured Light） | 投射圖案，由變形計算 3D | 三維量測、立體檢測 | 速度較慢、精度取決於投影解析度 |

### 相機選型

| 面向 | 面掃描相機（Area Scan） | 線掃描相機（Line Scan） |
|------|----------------------|----------------------|
| 取像方式 | 一次拍整個畫面 | 逐行掃描，物件需要移動 |
| 適用場景 | 靜態或低速移動物件 | 連續材料（紙張、薄膜、布料）、高速產線 |
| 解析度 | 受感測器尺寸限制 | 可透過移動距離達到超高解析度 |
| 觸發 | 外部觸發或連續取像 | 需要編碼器同步（Encoder Sync） |
| 整合難度 | 較低 | 較高（需要精確的速度同步） |

**選型簡則**：物件會停下來讓你拍 → 面掃描。物件持續移動且很長 → 線掃描。

### 與剔退系統的整合

視覺檢測發現不良品後，要能即時剔退。這個環節的設計重點：

- **延遲補償**：從「相機拍到」到「剔退機構動作」之間有處理時間和傳輸時間，要用追蹤（Tracking）功能補償
- **剔退確認**：用第二組感測器確認不良品確實被剔退了——不要只靠「有發剔退指令」就當作成功
- **誤剔退成本**：剔退演算法要平衡漏檢率（真不良沒被抓到）和誤殺率（好品被當不良剔退）。哪個成本更高取決於產品特性

## AMR/AGV 整合

### AGV vs AMR——不只是有沒有軌道

| 面向 | AGV（自動導引車） | AMR（自主移動機器人） |
|------|-----------------|-------------------|
| 導航方式 | 固定路徑（磁條、色帶、反光板） | 自主導航（SLAM、光達、視覺） |
| 路徑彈性 | 低——改路徑要改地面設施 | 高——軟體改路徑即可 |
| 障礙物處理 | 停下來等（或有限繞行） | 動態繞行 |
| 部署成本 | 初期低（車便宜），但地面工程有成本 | 初期高（車貴），但部署彈性 |
| 維護成本 | 地面設施磨損需維護 | 軟體更新、感測器校準 |
| 適合場景 | 固定路徑、大量重複搬運、戶外 | 路徑多變、環境複雜、需要彈性 |

### 車隊管理（Fleet Management）

多台 AMR/AGV 協同作業時，車隊管理系統是必要的：

| 功能 | 說明 | 重要性 |
|------|------|--------|
| 任務分配（Task Dispatch） | 決定哪台車去執行哪個任務 | 核心——直接影響搬運效率 |
| 交通管制（Traffic Control） | 防止車輛碰撞和死鎖 | 關鍵安全功能 |
| 充電管理（Charging Strategy） | 決定何時充電、充多久 | 影響車隊可用率。機會充電（Opportunity Charging）比跑到沒電再充效率高 |
| 路徑最佳化 | 動態計算最短/最快路徑 | 影響搬運節拍 |

### 與倉儲管理系統（WMS）的整合

AMR/AGV 不是獨立運作的——它們是物流系統的一部分：

- **搬運任務**由 WMS 或 MES 下達，不是由 AMR 自己決定
- **取放點**（Pick/Place Point）的精度要求取決於對接設備——和輸送帶對接 ±10mm 可能夠用，和機器人工站對接可能需要 ±2mm
- **安全標準**：ISO 3691-4（無人搬運車安全）是強制要求。人車共存區域的速度限制、感測器覆蓋範圍、急停距離都需要驗證

## PackML 包裝機械標準

PackML（ISA-TR88.00.02）定義了包裝機械的標準狀態模型，讓不同廠牌的設備能以統一的方式管理。

### 狀態模型

PackML 定義了 17 個狀態和 3 種操作模式（Production、Maintenance、Manual）。核心狀態流程：

```
IDLE → STARTING → EXECUTE → COMPLETING → COMPLETE → RESETTING → IDLE
  │                  │
  │                  ├── HOLDING → HELD → UNHOLDING → EXECUTE（暫停/恢復）
  │                  │
  │                  └── SUSPENDING → SUSPENDED → UNSUSPENDING → EXECUTE（上下游停滯）
  │
  └── STOPPING → STOPPED（正常停機）
  └── ABORTING → ABORTED（異常停機）
```

**關鍵區別**：
- **Held**：操作員主動暫停（例如要補料），恢復後繼續
- **Suspended**：外部原因導致暫停（例如下游滿了），條件恢復後自動繼續
- **Stopped**：正常的計畫停機
- **Aborted**：異常停機，需要確認原因後手動恢復

### 從 PackML 狀態計算 OEE

PackML 的狀態轉移和持續時間可以直接對應到 OEE 的三個維度：

| OEE 維度 | PackML 對應 | 計算方式 |
|---------|------------|---------|
| 可用率（Availability） | Execute 時間 / (Execute + Stopped + Held + Suspended + Aborting 時間) | 設備有多少時間在跑？ |
| 效能率（Performance） | 實際速度 / 設計速度 | 跑的時候有沒有達到應有速度？ |
| 良品率（Quality） | 良品數 / 總產出數 | 產出的東西有多少是好的？ |

> OEE 的完整分析方法和改善策略，參見 [quality-reliability.md](quality-reliability.md)。

## 機電整合實務

### 電氣設計（IEC 60204-1）

IEC 60204-1 是機械設備電氣安全設計的基礎標準。以下是最常被忽略但後果嚴重的要求：

| 要求 | 內容 | 常見違規 |
|------|------|---------|
| 主斷路器 | 每台設備必須有可上鎖的主斷路器（Lockable Main Disconnect） | 用一般斷路器代替，無法上鎖 |
| 急停（E-Stop） | 紅色蘑菇頭按鈕、黃色底板、自鎖式 | 顏色不對、位置不合理（操作員按不到） |
| 接地 | 保護接地導體不得小於相線截面（一定條件下） | 接地線太細、接地點不連續 |
| 控制電路電壓 | 控制電路建議 24VDC 或 120VAC 以下 | 控制電路用 220VAC，維護人員觸電風險高 |
| 電線顏色 | 保護接地：黃綠色。中性線：淺藍色 | 顏色混用 |

### 氣壓系統設計（ISO 5599）

| 設計要點 | 說明 | 常見問題 |
|---------|------|---------|
| 空氣品質 | ISO 8573-1 定義空氣品質等級。儀用空氣通常要求等級 1.4.1（固體粒子/水分/油分） | 沒有空氣處理組件（FRL），直接接廠務壓縮空氣 |
| 閥島配置 | 用閥島（Valve Island）取代分散的獨立電磁閥，減少配管和佈線 | 閥島位置離氣缸太遠，管路延遲影響動作速度 |
| 氣缸選型 | 缸徑根據負載力計算，行程根據動作距離，不要過大過小 | 「反正壓力夠大」就選最小缸徑——忽略了摩擦力和安全係數 |
| 洩壓（Exhaust） | 系統斷電或急停時，氣壓系統要能安全洩壓 | 沒有洩壓閥，停機後殘餘氣壓導致意外動作 |

### 電磁相容性（EMC/EMI）

| 干擾源 | 典型來源 | 防護措施 |
|-------|---------|---------|
| 傳導干擾 | 變頻器（VFD）、開關電源 | 電源濾波器（EMI Filter）、隔離變壓器 |
| 輻射干擾 | 高頻通訊、伺服驅動器 | 遮蔽電纜（Shielded Cable）、正確的遮蔽接地 |
| 接地迴路 | 多點接地造成的電位差 | 單點接地或等電位接地網路 |

**最常見的 EMI 問題**：變頻器的輸出電纜沒有使用遮蔽線，干擾旁邊的類比信號。解法：變頻器輸出一定要用遮蔽線，遮蔽層兩端接地。

### 接地最佳實務

```
                    ┌─── 設備接地匯流排 ───┐
                    │                      │
              ┌─────┼──────┐        ┌──────┼─────┐
              │     │      │        │      │     │
           馬達  變頻器  控制櫃    馬達  變頻器  控制櫃
           接地  接地    接地      接地  接地    接地
                    │                      │
                    └────── 廠區接地系統 ──────┘
```

- **控制信號接地**和**馬達/動力接地**要分開
- 類比信號的遮蔽層只在控制器端單點接地（避免接地迴路）
- 數位通訊線的遮蔽層依協定規範——有的要兩端接地（例如 PROFINET），有的要單端

### 線槽與電纜管理

| 原則 | 說明 |
|------|------|
| 動力線和信號線分槽 | 動力線（馬達、加熱器）和控制信號線至少相距 200mm 或使用隔板 |
| 彎曲半徑 | 拖鏈內的電纜彎曲半徑至少為電纜外徑的 10 倍（高柔性電纜可放寬到 7.5 倍） |
| 標示 | 每條線的兩端都要有標示，標示系統一致（和電氣圖紙對應） |
| 備用容量 | 線槽填充率不超過 60-70%——留給未來擴充和散熱 |

## 常見踩坑

### 伺服調參失敗

**症狀**：馬達震動、定位超調（Overshoot）、或者完全不動。

**根因分類與對策**：

| 症狀 | 最可能原因 | 處理方式 |
|------|-----------|---------|
| 高頻震動（嗡嗡聲） | 增益太高（剛性設定過高） | 降低速度迴路增益（Kp），增加速度迴路積分時間（Ti） |
| 定位超調 | 位置迴路增益太高、或加減速時間太短 | 降低位置迴路增益、延長加減速時間 |
| 低頻擺動 | 機械共振被激發 | 啟用陷波濾波器（Notch Filter），找出共振頻率 |
| 完全不動 | 抱閘沒鬆開、編碼器接線錯誤、或正反轉設定反了 | 從最基礎的硬體接線檢查開始 |

**調參黃金法則**：先跑自動調參（Auto-Tuning）取得基線參數 → 用低速低負載測試 → 逐步提高速度和負載 → 微調。不要一開始就手動從零調。

### PLC 掃描時間意外

**症狀**：程式邏輯正確，但實際行為和預期不一致。快速信號被遺漏。

**根因**：PLC 的掃描週期（Scan Cycle）比信號變化還慢。

| 場景 | 問題 | 解法 |
|------|------|------|
| 高速計數 | 脈衝頻率超過 PLC 掃描速率，漏計 | 使用高速計數器模組（HSC），不要用一般數位輸入 |
| 短脈衝偵測 | 信號寬度 < 一個掃描週期，PLC 完全看不到 | 用中斷（Interrupt）或硬體鎖存（Latch） |
| 多工作負載 | 程式太長導致掃描時間變長 | 分析各任務的執行時間，必要時分優先等級（Task Priority） |

**重要提醒**：安全相關的輸入不能依賴正常掃描——必須使用專用安全模組或硬體聯鎖。

### 機器人工具中心點校正（TCP Calibration）

**症狀**：機器人示教的點位正確，但換了工具或碰撞後位置偏了。

**根因**：工具中心點（Tool Center Point, TCP）定義不準確或已偏移。

**處理流程**：
1. TCP 校正應該在設備安裝、工具更換、和碰撞後都要做
2. 使用四點法或六點法校正——機器人從不同姿態讓工具尖端對準同一個固定點
3. 校正精度要驗證——在不同姿態下移動到同一個笛卡爾座標點，觀察實際位置偏差
4. 保留校正前的參數備份——萬一新的校正更差可以回復

### 機器視覺照明環境變化

**症狀**：視覺系統白天正常、晚上誤判，或者隨季節天氣變化效果不穩定。

**根因**：環境光（日光、廠房照明）影響了視覺系統的成像品質。

**解法**：
- 最根本的解法是**遮光**——用遮光罩或暗箱隔絕環境光
- 如果無法完全遮光，用高強度主動照明壓過環境光
- 使用窄頻帶通濾光鏡（Bandpass Filter）搭配對應波長的照明——只讓特定波長的光進入相機
- 在不同環境光條件下做驗證——不要只在深夜或假日工廠關燈時驗收

### 數位 I/O 交握的邏輯陷阱

**症狀**：兩台設備的數位 I/O 交握偶爾失敗——設備 A 以為 B 已經完成，但 B 還沒準備好。

**根因**：交握信號的時序競態（Timing Race Condition）。

**典型案例**：
```
設備 A 送出「取走完成」信號 → 設備 B 看到信號 → B 送出「可以放下一個」
                                                        ↑
                                              如果 A 太快放下信號
                                              B 可能看到瞬間的「完成」
                                              就誤以為第二次取走也完成了
```

**解法**：
- 使用完整的四步交握（Four-Step Handshake）：發出 → 確認 → 撤回 → 確認撤回
- 每個信號的持續時間要設最小保持時間（例如 ≥ 2 個掃描週期）
- 如果交握變得很複雜（超過 8 個信號），認真考慮改用現場匯流排通訊
