## 協定選型決策樹

不要從「哪個協定最好」出發——從你的具體場景出發。

### 我的設備是什麼？

| 設備 / 場景 | 首選協定 | 備選 | 說明 |
|------------|---------|------|------|
| Siemens S7-1200/1500 → MES | OPC UA（內建） | S7 協定（透過閘道器） | S7-1500 原生支援 OPC UA Server，直接連 |
| Mitsubishi iQ-R → 資料平台 | OPC UA 或 CC-Link IE | SLMP（Socket 通訊） | 用三菱的 OPC UA 模組，或透過 CC-Link IE TSN |
| Rockwell ControlLogix → 上位 | EtherNet/IP（CIP） | OPC UA（FactoryTalk） | Rockwell 生態系首選 EtherNet/IP |
| 老舊 PLC（無乙太網口） | Modbus RTU → 閘道器 | 硬體升級 | RS-485 轉 Modbus TCP 閘道器是最低成本方案 |
| 半導體設備 → EAP 主機 | SECS/GEM（HSMS） | EDA（SEMI E120+） | SEMI 標準強制要求，沒有替代方案 |
| 數百個感測器 → 雲端 | MQTT + Sparkplug B | OPC UA Pub/Sub | 輕量、頻寬友善、天生適合多對多 |
| 伺服馬達 + 運動控制 | EtherCAT | PROFINET IRT | 需要微秒級同步，EtherCAT 週期最短 |
| 智慧感測器（近端數位化） | IO-Link | 4-20mA + HART | IO-Link 支援參數化和診斷，下一代感測器標配 |
| 多系統資料匯整 | UNS（MQTT 架構） | OPC UA Aggregation Server | 見 [architecture-design.md](architecture-design.md) 的 UNS 章節 |

### 我需要什麼層級的即時性？

| 即時性需求 | 適用協定 | 典型延遲 |
|----------|---------|---------|
| 硬即時（Hard Real-Time）：運動控制、同步軸 | EtherCAT、PROFINET IRT、SERCOS III | < 1ms，抖動 < 1μs |
| 軟即時（Soft Real-Time）：閉迴路控制 | PROFINET RT、EtherNet/IP（隱性訊息） | 1-10ms |
| 準即時（Near Real-Time）：SCADA 監控 | OPC UA、Modbus TCP | 10-500ms |
| 非即時（Non Real-Time）：報表、歷史趨勢 | MQTT、REST API、資料庫查詢 | 秒到分鐘級 |

## OPC UA

### 基本架構

OPC UA（IEC 62541）有兩種通訊模式：

| 模式 | 運作方式 | 適合場景 |
|------|---------|---------|
| 用戶端-伺服器（Client-Server） | 用戶端主動連線伺服器，訂閱或輪詢資料 | 傳統 SCADA/MES 整合、點對點取值 |
| 發布-訂閱（Pub/Sub） | 發布者將資料發送到多播位址或代理，訂閱者接收 | 控制器對控制器（C2C）、大量消費端、與 TSN 結合 |

### 資訊模型是 OPC UA 的真正價值

很多人把 OPC UA 當作「比較新的 OPC DA」，這是低估了它。OPC UA 的殺手級功能是**資訊模型（Information Model）**：

- 不只傳數值，還傳語義：這個值代表什麼、單位是什麼、跟其他值的關係是什麼
- 設備製造商可以發布**伴侶規範（Companion Specification）**，定義特定設備類型的標準資料模型
- 已發布的伴侶規範超過 80 個，涵蓋機器人（VDMA）、包裝機（PackML）、注塑機、CNC 等

### OPC UA 安全模型

OPC UA 內建三層安全機制，在工業環境中這是優勢：

| 層級 | 機制 | 說明 |
|------|------|------|
| 傳輸層 | TLS 加密 | 資料在傳輸過程中加密 |
| 應用層 | X.509 憑證 | 用戶端和伺服器互相驗證身份 |
| 使用者層 | 帳號密碼 / 憑證 | 控制誰能存取哪些節點 |

**實務提醒**：安全機制預設經常被關閉（設定為 None/Anonymous），因為「開了之後連不上」。這等於把門鎖上但鑰匙插在門上。部署時務必正確設定安全策略。

### 什麼時候 OPC UA 是正確選擇？

| 場景 | 推薦程度 | 理由 |
|------|---------|------|
| PLC/DCS → MES/SCADA 整合 | 強烈推薦 | 語義豐富、跨廠牌、安全機制完整 |
| 設備標準化介面（伴侶規範存在） | 強烈推薦 | 買到的設備直接支援，減少客製 |
| 數百台小型感測器 → 雲端 | 不推薦 | 過重，用 MQTT 更合適 |
| 微秒級運動控制 | 不推薦（單獨使用） | 需搭配 TSN 或使用專用即時協定 |
| 嵌入式設備資源受限 | 視情況 | OPC UA Nano Profile 可用，但資源佔用仍比 MQTT 高 |

## MQTT 與 Sparkplug B

### MQTT 基礎與版本選擇

MQTT（Message Queuing Telemetry Transport）是輕量級的發布-訂閱（Pub/Sub）協定。發布者發送訊息到主題（Topic），訂閱者訂閱感興趣的主題，中間由代理（Broker）負責轉發。

**版本建議**：新專案一律用 MQTT v5（支援使用者屬性、詳細原因碼、主題別名、訊息到期、共享訂閱）。v3.1.1 只有在配合 Sparkplug B 規範時才需要。

### Sparkplug B 詳解

Sparkplug B 在 MQTT 之上定義了工業場景的標準化行為。核心機制已在 [architecture-design.md](architecture-design.md) 的 UNS 章節說明，此處補充實作細節。

#### 主題命名空間

```
spBv1.0/{group_id}/{message_type}/{edge_node_id}/{device_id}
```

訊息類型（message_type）：

| 類型 | 發送者 | 說明 |
|------|--------|------|
| NBIRTH | 邊緣節點 | 節點上線，包含所有指標定義 |
| NDEATH | MQTT 代理（遺囑） | 節點異常斷線 |
| NDATA | 邊緣節點 | 節點層級的資料更新（僅變動的值） |
| NCMD | 應用端 | 對節點下指令 |
| DBIRTH | 邊緣節點 | 設備上線 |
| DDEATH | 邊緣節點 | 設備離線 |
| DDATA | 邊緣節點 | 設備層級的資料更新 |
| DCMD | 應用端 | 對設備下指令 |
| STATE | 主要應用 | SCADA/主應用的上線/離線狀態 |

#### 異動回報（Report by Exception, RBE）

Sparkplug B 預設只在值發生變化時才發送資料，而不是固定週期全量上報。這大幅降低網路流量，但也帶來一個陷阱：如果消費端錯過了 BIRTH 訊息，它就不知道完整的指標清單和初始值。

**解法**：消費端必須能處理「先收到 BIRTH，再收到 DATA」的流程。如果遲到加入，要能向代理請求最新的 BIRTH 訊息（透過保留訊息機制）。

### MQTT vs OPC UA：不是非此即彼

| 面向 | MQTT | OPC UA |
|------|------|--------|
| 資料模型 | 無（靠 Sparkplug B 補足） | 豐富的語義資訊模型 |
| 通訊模式 | 發布-訂閱 | 用戶端-伺服器 + 發布-訂閱 |
| 資源佔用 | 極低（適合嵌入式） | 較高（完整堆疊約 20-50MB RAM） |
| 安全機制 | TLS + 帳號密碼（需自行管理） | 內建 X.509 + 應用層安全 |
| 適合角色 | 資料分發、多對多消費 | 設備整合、語義互通 |
| 典型位置 | 廠級/企業級整合 | 邊緣層設備連線 |

**老手的常見做法**：邊緣用 OPC UA 讀設備，轉成 Sparkplug B 發布到 MQTT 代理做廠級分發。兩者互補，不衝突。

## SECS/GEM

### 為什麼半導體離不開 SECS/GEM？

SEMI（國際半導體產業協會）標準中，SECS/GEM 是設備與工廠自動化主機（EAP Host）之間的標準介面。在半導體廠，不支援 SECS/GEM 的設備就進不了產線。

### 協定堆疊

```
┌──────────────────────────┐
│  GEM（SEMI E30）          │ ← 設備行為模型（狀態機、遠端指令、警報、配方管理）
├──────────────────────────┤
│  SECS-II（SEMI E5）      │ ← 訊息格式定義（資料項目、串流/功能碼）
├──────────────────────────┤
│  HSMS（SEMI E37）        │ ← TCP/IP 傳輸層（取代早期的 RS-232 SECS-I）
└──────────────────────────┘
```

### SECS-II 訊息結構（SEMI E5）

每個 SECS-II 訊息由**串流編號（Stream）**和**功能編號（Function）**標識，寫做 `SxFy`。

| 串流 | 用途 | 常用功能 |
|------|------|---------|
| S1 | 設備狀態 | S1F1（上線確認）、S1F3/S1F4（狀態變數查詢） |
| S2 | 設備控制 | S2F13/S2F14（設備常數查詢）、S2F41/S2F42（主機指令） |
| S5 | 警報管理 | S5F1/S5F2（警報通報）、S5F3/S5F4（啟用/停用警報） |
| S6 | 資料收集 | S6F11/S6F12（事件報告）、S6F15/S6F16（事件報告查詢） |
| S7 | 配方管理 | S7F1-S7F6（配方上傳/下載/驗證） |
| S10 | 終端機訊息 | S10F1/S10F2（設備對操作員的文字通知） |
| S14 | 物件服務 | S14F1/S14F2（物件讀寫，GEM300 使用） |

#### 訊息格式範例

S1F3（狀態變數查詢請求）：
```
S1F3 W
  <L [2]
    <U4 1001>       ← 狀態變數 ID：腔體壓力
    <U4 1002>       ← 狀態變數 ID：基板溫度
  >
```

S1F4（回覆）：
```
S1F4
  <L [2]
    <F4 2.35>       ← 腔體壓力值（Torr）
    <F4 350.2>      ← 基板溫度值（°C）
  >
```

資料項目型態代碼：

| 代碼 | 型態 | 說明 |
|------|------|------|
| L | List | 清單，包含子項目 |
| B | Binary | 二進位 |
| Bo | Boolean | 布林 |
| A | ASCII | 字串 |
| U1/U2/U4/U8 | Unsigned Int | 無號整數（1/2/4/8 位元組） |
| I1/I2/I4/I8 | Signed Int | 有號整數 |
| F4/F8 | Float | 浮點數（4/8 位元組） |

### GEM 狀態模型（SEMI E30）

GEM 定義了設備的標準行為模型。其中最重要的是**通訊狀態模型**和**控制狀態模型**。

#### 通訊狀態模型

`DISABLED → ENABLED(NOT COMMUNICATING) → ENABLED(COMMUNICATING)`

進入通訊狀態（COMMUNICATING）的條件是成功交換 S1F13/S1F14。

#### 控制狀態模型

| 狀態 | 說明 | 主機權限 |
|------|------|---------|
| 設備離線（Equipment Offline） | 設備由現場操作員控制 | 無 |
| 主機離線（Host Offline） | 設備已連線但等待主機授權 | 無 |
| 本地模式（Online Local） | 主機可監控但操作員優先 | 唯讀 |
| 遠端模式（Online Remote） | 主機完全控制——自動化產線的目標狀態 | 完全控制 |

轉換路徑：Equipment Offline → Host Offline → Online（Local 或 Remote）。

### 遠端指令（RCMD, S2F41）

主機透過 S2F41 對設備下達指令。結構：

```
S2F41 W
  <L [2]
    <A "PP-SELECT">          ← 指令名稱
    <L [1]
      <L [2]
        <A "PPID">           ← 參數名稱
        <A "RECIPE_001">     ← 參數值
      >
    >
  >
```

設備回覆 S2F42 的 HCACK（主機指令確認碼）：

| HCACK | 意義 |
|-------|------|
| 0 | 確認，指令已被接受 |
| 1 | 指令不存在 |
| 2 | 無法執行（設備狀態不允許） |
| 3 | 至少一個參數無效 |
| 4 | 確認，但尚未完成（非同步） |
| 5 | 拒絕，已有指令執行中 |

### HSMS 連線建立（SEMI E37）

HSMS（High-Speed SECS Message Services）取代了老舊的 RS-232，用 TCP/IP 承載 SECS-II 訊息。

連線建立流程：

1. **被動端（Passive）**監聽 TCP 埠（預設 5000 起跳）
2. **主動端（Active）**發起 TCP 連線
3. 連線建立後，主動端發送 **Select.req** 控制訊息
4. 被動端回覆 **Select.rsp**
5. HSMS 會話建立完成，可以開始交換 SECS-II 訊息

**角色慣例**：設備通常是被動端，EAP 主機通常是主動端。但這不是強制的——要看設備供應商的實作。

**T3 計時器（回覆超時）**：發送訊息後，如果在 T3 時間內沒收到回覆，視為通訊異常。典型值 45 秒。在生產環境中，這個值的設定需要根據設備的實際回應速度調整。

#### HSMS 計時器完整表

| 計時器 | 用途 | 典型值 | 設定建議 |
|--------|------|--------|---------|
| T1 | 字元間超時（僅 SECS-I，HSMS 不用） | — | — |
| T2 | 協定超時（HSMS 不用） | — | — |
| T3 | 回覆超時 | 45s | 根據設備最慢回應調整，配方下載可能需要更長 |
| T5 | 連線分離超時（重連等待） | 10s | 不要設太短，避免頻繁重連 |
| T6 | 控制交易超時 | 5s | 保持預設 |
| T7 | 非選擇狀態超時（TCP 連了但沒做 Select） | 10s | 防止幽靈連線佔資源 |
| T8 | 網路字元間超時 | 5s | TCP 層基本上不會觸發 |
| Link Test | 心跳間隔 | 30-120s | 太短浪費頻寬，太長偵測慢 |

## Modbus TCP/RTU

### 為什麼 Modbus 到處都是？

因為簡單。1979 年 Modicon 發明的協定，至今仍然是最廣泛支援的工業通訊協定。幾乎每一台有通訊口的工業設備都支援 Modbus。

### 暫存器映射（Register Map）

Modbus 的資料模型就是四種暫存器：

| 類型 | 位址範圍 | 讀/寫 | 資料寬度 | 用途 |
|------|---------|-------|---------|------|
| 線圈（Coil） | 00001-09999 | 讀寫 | 1 bit | 數位輸出（DO） |
| 離散輸入（Discrete Input） | 10001-19999 | 唯讀 | 1 bit | 數位輸入（DI） |
| 輸入暫存器（Input Register） | 30001-39999 | 唯讀 | 16 bit | 類比輸入（AI） |
| 保持暫存器（Holding Register） | 40001-49999 | 讀寫 | 16 bit | 設定值、參數 |

### 位元組順序（Byte Order）問題——必讀

這是 Modbus 整合中最常見的坑。Modbus 每個暫存器是 16 位元。但 32 位元的浮點數需要佔 2 個暫存器。問題來了：**這 2 個暫存器的排列順序沒有統一標準**。

| 排列方式 | 暫存器 40001 | 暫存器 40002 | 說明 |
|---------|-------------|-------------|------|
| Big-Endian（AB CD） | 高位元組 | 低位元組 | Modicon 原始慣例 |
| Little-Endian（CD AB） | 低位元組 | 高位元組 | 部分設備採用 |
| Mid-Big（BA DC） | 位元組反轉的高位 | 位元組反轉的低位 | 混合模式 |
| Mid-Little（DC BA） | 位元組反轉的低位 | 位元組反轉的高位 | 混合模式 |

**四種排列方式讀出來的值完全不同。** 如果你讀到一個看起來不合理的浮點數（例如溫度值顯示 1.73e+38），八成是位元組順序設錯了。

**排查步驟**：
1. 查設備手冊，找位元組順序說明（很多手冊沒寫，需要實測）
2. 讀兩個暫存器的原始十六進位值
3. 對照設備面板上的實際顯示值
4. 嘗試四種排列，看哪種結果正確

### Modbus TCP vs RTU

| 面向 | Modbus RTU | Modbus TCP |
|------|-----------|-----------|
| 傳輸媒介 | RS-485（最常見）或 RS-232 | 乙太網 TCP/IP |
| 拓撲 | 匯流排（Bus），一主多從 | 星狀，可多主 |
| 位址範圍 | 1-247（從站位址） | IP 位址 + 單元識別碼（Unit ID） |
| 最大距離 | RS-485 約 1200m | 乙太網標準距離 |
| 速度 | 9600-115200 bps | 10/100 Mbps |
| 每次最大讀取 | 125 個暫存器（250 位元組） | 同上（Modbus 協定限制） |

### 什麼時候該升級掉 Modbus？

| 信號 | 建議 |
|------|------|
| 需要讀取的暫存器超過數百個，輪詢週期過長 | 升級到 OPC UA 或 EtherNet/IP |
| 需要語義化的資料模型（不只是暫存器編號） | 升級到 OPC UA |
| 需要安全認證和加密 | Modbus 沒有內建安全機制，必須靠網路層保護或升級協定 |
| 設備數量多且分散，佈線困難 | 考慮無線方案或 IO-Link |
| 但設備穩定運行、需求簡單、沒有安全疑慮 | **不要升級**。能用就不要動 |

## 工業以太網家族

### 主要成員比較

| 協定 | 主導者 | 即時等級 | 典型週期 | 拓撲 | 生態 |
|------|--------|---------|---------|------|------|
| EtherNet/IP | ODVA（Rockwell 推動） | 軟即時 | 1-10ms | 星/環/線 | 北美市場、Rockwell 生態 |
| PROFINET | PI（Siemens 推動） | RT: 軟即時 / IRT: 硬即時 | RT: 1-10ms / IRT: <1ms | 星/線/環 | 歐洲市場、Siemens 生態 |
| EtherCAT | ETG（Beckhoff 推動） | 硬即時 | <100μs | 線型（菊花鏈） | 運動控制、半導體設備 |
| CC-Link IE TSN | CLPA（Mitsubishi 推動） | 硬即時（TSN 基礎） | <31.25μs | 星/線/環 | 亞洲市場、Mitsubishi 生態 |
| SERCOS III | SERCOS Int'l | 硬即時 | <62.5μs | 環型 | CNC、運動控制 |
| POWERLINK | EPSG（B&R 推動） | 硬即時 | <100μs | 線/星 | 包裝機械、B&R 生態 |

### 選型指引——直接給建議

| 場景 | 首選 | 理由 |
|------|------|------|
| 全 Siemens 產線 | PROFINET | 原生整合最佳，工具鏈完整 |
| 全 Rockwell 產線 | EtherNet/IP | 同上 |
| 全 Mitsubishi 產線 | CC-Link IE TSN | 同上 |
| 高精度運動控制（多軸同步） | EtherCAT | 週期最短、同步精度最高、拓撲效率最優 |
| 半導體設備內部 | EtherCAT | 半導體設備商大量採用，供應鏈成熟 |
| 混合品牌產線 | 看比例決定；若無主導品牌，EtherNet/IP 或 PROFINET 通用性較好 | — |
| 新建廠且考慮未來融合 | CC-Link IE TSN 或 PROFINET over TSN | TSN 是長期方向 |

### 互通性挑戰

現實中，同一座工廠裡常常有多種工業以太網協定共存。互通的做法：

1. **閘道器（Gateway）**：協定 A ↔ 閘道器 ↔ 協定 B。最常見但增加延遲和故障點。
2. **OPC UA 做為統一介面**：各協定用自己的方式到邊緣，然後統一透過 OPC UA 往上報。語義損失最小。
3. **TSN 融合**：未來方向，用 TSN 做為共同的乙太網基礎，不同協定在上面共存。但目前（2026 年）各家的 TSN 整合仍在進行中。

## IO-Link

IO-Link（IEC 61131-9）是感測器和致動器的最後一哩數位化標準，把傳統 4-20mA 類比訊號升級為雙向數位通訊，同時保持相容既有的三線佈線。架構為：感測器/致動器 ↔ IO-Link Master ↔ PLC/邊緣閘道器。

### IO-Link 帶來的三個改變

| 改變 | 實際效益 |
|------|---------|
| 參數化（Parameterization） | 換同型感測器時自動下載參數，免現場手動設定 |
| 診斷（Diagnostics） | 感測器主動回報健康狀態，在完全失效前介入 |
| 程序資料 + 事件（Process Data + Events） | 取代「4-20mA 只能傳一個值」的限制 |

### 與上層協定的整合

IO-Link Master 透過上層工業以太網整合進控制系統：PROFINET（Siemens 生態最常見）、EtherNet/IP（Rockwell）、EtherCAT（運動控制）、OPC UA（語義化整合，伴侶規範已發布）。部分 Master 也內建 MQTT 發布，可跳過 PLC 直接連資料平台。

## 時間敏感網路

### TSN 解決什麼問題？

時間敏感網路（Time-Sensitive Networking, TSN）是 IEEE 802.1 的一組子標準，目的是讓標準乙太網支援**確定性延遲和時間同步**。白話說：讓一般的乙太網交換器也能跑即時控制流量，不需要專用的工業以太網硬體。

### 關鍵子標準

| 標準 | 功能 | 白話說明 |
|------|------|---------|
| IEEE 802.1AS | 時間同步（gPTP） | 全網路的設備對齊到奈秒級的共同時鐘 |
| IEEE 802.1Qbv | 時間感知排程器（TAS） | 為即時流量預留專屬時間窗口，保證不被其他流量干擾 |
| IEEE 802.1Qcc | 串流預留（SRP） | 集中式管理，自動配置哪些流量走哪些路徑 |
| IEEE 802.1CB | 幀複製與消除（FRER） | 關鍵封包走兩條路，到目的地去重複，實現零丟包冗餘 |
| IEEE 802.1Qci | 每串流過濾與管制 | 防止異常流量影響即時通道，也有資安效果 |

### TSN 目前的成熟度（2026 年狀態）

| 面向 | 狀態 | 說明 |
|------|------|------|
| 標準制定 | 大致完成 | 核心子標準已發布 |
| 矽片支援 | 可用 | Intel、TI、NXP、Marvell 都有 TSN 交換器晶片 |
| 交換器產品 | 商用中 | Cisco IE、Belden/Hirschmann、Moxa 等都有產品 |
| 控制器支援 | 逐步導入 | CC-Link IE TSN 已量產；PROFINET over TSN 有產品；EtherNet/IP over TSN 較慢 |
| 設定管理工具 | 尚不成熟 | 集中式網路設定（CNC / CUC）標準仍在收斂中 |
| 跨廠牌互通 | 進行中 | TSN 測試平台（Testbed）在驗證，但實際跨廠牌部署案例仍有限 |

### 遷移路徑

**務實建議**：不要等 TSN 完全成熟才行動，但也不要現在就把賭注全押在 TSN 上。

1. **新建產線**：選用 TSN-Ready 的交換器和控制器，即使暫時不啟用 TSN 功能
2. **既有產線**：維持現有工業以太網協定，不需要為了 TSN 做大規模更換
3. **技術儲備**：在實驗室建一組 TSN 測試環境，熟悉設定和除錯
4. **關注趨勢**：OPC UA over TSN + FLC（Field Level Communications）是最被看好的融合方向

## 多協定共存策略

### 現實永遠是多協定的

沒有一座工廠只用一種協定。典型的半導體廠：

- 設備通訊：SECS/GEM（HSMS）
- 設備內部控制：EtherCAT
- 廠務監控：Modbus TCP
- 資料平台整合：OPC UA + MQTT
- 老設備：Modbus RTU、DeviceNet、甚至 4-20mA

### 閘道器模式（最常見）

各設備透過閘道器統一轉換為 OPC UA 或 MQTT 後再往上送。閘道器選型六要素：支援的協定數量（只要夠用，不是越多越好）、同時連線數上限、資料映射彈性（暫存器對應 + 單位轉換）、斷線時的緩衝能力、管理介面（設定匯出/匯入）、冗餘機制。

### 資料模型對齊——比協定轉換難十倍

協定轉換是「格式問題」，有工具就能解。但**資料語義的對齊**是「意義問題」，需要人去定義。

| 對齊面向 | 常見問題 | 解決方法 |
|---------|---------|---------|
| 命名 | 同一個感測器在不同系統裡名字不同 | 建立全廠統一的標籤命名規範（見 [architecture-design.md](architecture-design.md) 的 UNS 章節） |
| 單位 | m³/h vs GPM vs L/min | 在資料字典中明確定義，閘道器做轉換 |
| 精度 | 來源是 16 位元整數，上位系統要 32 位元浮點 | 定義縮放係數和偏移量 |
| 時間 | 不同設備的時間戳基準不同 | 全廠 NTP/PTP 同步，閘道器加上統一時間戳 |
| 狀態碼 | 系統 A 用 0/1，系統 B 用字串 "RUN/STOP" | 建立狀態碼映射表，納入版本管理 |
| 品質碼 | OPC 有品質碼，Modbus 沒有 | 在閘道器層面補上品質碼：通訊正常/超時/範圍異常 |

**特別注意品質碼**：沒有品質碼（Quality Code）的協定（如 Modbus），下游系統無法區分「值是 0（合法量測）」與「值是 0 因為感測器斷線」。在閘道器層一定要補上品質標記。

## 常見踩坑

| 類別 | 踩坑 | 根因 | 修復 |
|------|------|------|------|
| 協定 | Modbus 浮點值亂碼 | 位元組順序設定錯誤 | 嘗試四種排列方式，對照設備面板確認 |
| 協定 | OPC UA 連線頻繁中斷 | Session Timeout 與 Publishing Interval 不匹配 | 伺服器 Timeout 要大於用戶端 Interval |
| 協定 | SECS/GEM 通訊建立失敗 | HSMS 主被動角色設反 | 確認哪端 Active、哪端 Passive |
| 協定 | MQTT 訊息遺失 | QoS 0 或代理未持久化 | 關鍵資料用 QoS 1+，啟用持久化 |
| 協定 | EtherCAT 一台斷全鏈斷 | 菊花鏈拓撲固有限制 | 冗餘環型拓撲，關鍵設備放鏈路前端 |
| 時間 | 事件時序錯亂 | 各設備時鐘未同步 | 全廠 NTP（ms 級）或 PTP（μs 級） |
| 時間 | 資料合併對不齊 | 閘道器用「收到時間」而非「產生時間」 | 盡量使用來源設備的原始時間戳 |
| 時間 | 歷史資料有空洞 | Sparkplug B 異動回報，值沒變不送 | 補充定期心跳或全量快照 |
| 網路 | OPC UA 被防火牆擋 | TCP 4840 未開放 | 開放埠號但限制來源 IP |
| 網路 | MQTT 穿不過企業防火牆 | TCP 1883/8883 被封 | 用 MQTT over WebSocket（TCP 443） |
| 網路 | Modbus 跨網段不通 | Unit ID 混淆或路由問題 | 確認 Unit ID 映射，檢查路由表 |
| 網路 | 工業以太網被一般流量淹沒 | OT 與 IT 共用交換器 | VLAN 或實體隔離 |
| 編碼 | SECS/GEM 配方名稱亂碼 | SECS-II ASCII 不支援多位元組字元 | 配方名稱限 ASCII，中文放註解欄位 |
| 編碼 | OPC UA 中文標籤亂碼 | 用戶端未正確處理 UTF-8 | 確認字元編碼設定 |
| 編碼 | Modbus 字串前後顛倒 | 字元在暫存器中排列不統一 | 查設備文件確認高低位元組排列 |
