## 半導體製造的特殊性

晶圓廠和一般製造業的差異不只是「比較精密」這麼簡單。以下特性深刻影響系統設計的每個決策：

### 為什麼晶圓廠不能套用一般製造業的思維？

| 特性 | 一般離散製造 | 晶圓廠 | 對系統設計的影響 |
|------|------------|-------|----------------|
| 環境等級 | 一般車間 | 無塵室（Cleanroom, ISO Class 1-5） | 所有硬體佈建需配合微污染防治（AMC），設備進出需經過嚴格管控 |
| 生產單位 | 件、批 | 晶圓批（Lot）→ 晶圓（Wafer）→ 晶粒（Die） | 追蹤粒度到每片晶圓甚至每顆晶粒，資料量爆炸式成長 |
| 製程步驟 | 數十步 | 五百到一千步以上 | 配方管理（Recipe Management）是核心，錯一步就是整批報廢 |
| 精度要求 | 微米到毫米 | 奈米等級（先進製程 < 3nm） | 設備參數偏移零點幾個百分比就可能造成良率崩潰 |
| 設備成本 | 數十萬到數百萬 | 極紫外光微影機（EUV）一台超過一億美元 | 設備稼動率（Uptime）直接影響投資回報，每小時停機成本極高 |
| 產品多樣性 | 高度客製 | 同一產線可能跑多種製程節點與產品 | 批次管理（Lot Management）和排程最佳化是永恆挑戰 |
| 週期時間 | 小時到天 | 數週到數月（Cycle Time 通常 40-60 天） | 在製品（WIP）管理和瓶頸分析至關重要 |
| 資料量 | 中等 | 每台設備每天產生數 GB 到數十 GB 時序數據 | 資料架構設計從第一天就不能馬虎 |

### 配方驅動的製造模式

晶圓廠是典型的「配方驅動」（Recipe-Driven）製造。每一步製程靠配方控制：

- **主配方**（Master Recipe）：定義製程參數的標準值
- **控制配方**（Control Recipe）：根據先進製程控制（APC）調整後的實際執行版本
- **配方管理**是資安和品質的交叉點——錯誤的配方上傳可能導致數百萬美元損失

> ⚠️ 配方保護是晶圓廠最敏感的智財之一。系統設計必須確保配方的完整性（Integrity）、機密性（Confidentiality）和可追溯性（Traceability）。SEMI E187 對此有明確要求。

## SEMI 標準全景圖

SEMI 標準體系龐大，但系統整合工程師真正需要掌握的可以按功能分群。以下按實際使用頻率和重要性排列。

### 設備通訊標準（Equipment Communication）

這組標準定義設備和主機（Host）之間如何溝通。是晶圓廠自動化的基礎。

| 標準 | 名稱 | 定位 | 實務重點 |
|------|------|------|---------|
| **E5** | SECS-II | 訊息格式定義 | 定義訊息結構（Stream/Function），所有 SECS 通訊的基礎層 |
| **E30** | GEM | 通用設備模型 | 定義設備行為模型——狀態機、變數、事件、警報、遠端指令。**必讀** |
| **E37** | HSMS | 高速訊息傳輸 | TCP/IP 上的傳輸層，取代舊的 RS-232（E4/SECS-I）。現代設備全用 HSMS |
| **E40** | PJM | 製程作業管理 | 定義製程作業（Process Job）生命週期，控制晶圓在設備內的加工流程 |
| **E87** | CMS | 載具管理 | 管理 FOUP/SMIF 等載具的狀態追蹤——開門、關門、對位、卸載 |
| **E90** | STS | 基板追蹤 | 追蹤每片晶圓的位置和狀態——在載具裡？在腔體裡？加工完了？ |
| **E94** | CJM | 控制作業管理 | 比 E40 高一層，管理控制作業（Control Job），協調多個製程作業 |
| **E116** | ERM | 設備回收管理 | 處理異常後的回復流程——設備出錯後如何安全地恢復到可用狀態 |

> 💡 **GEM300 = E40 + E87 + E90 + E94 + E116 + E30（300mm 擴充）**
> 這是 300mm 晶圓廠的標準自動化協定組合。所有 300mm 設備都必須支援 GEM300。200mm 廠通常只需要 E5 + E30 + E37。

### 設備數據標準（Equipment Data Acquisition, EDA）

這組標準解決「如何從設備大量擷取數據」的問題。是先進製程控制（FDC、APC、VM）的數據基礎。

| 標準 | 名稱 | 定位 | 實務重點 |
|------|------|------|---------|
| **E120** | CDA | 通用設備模型（數據面） | 定義設備的層級結構和元數據模型——設備由哪些模組組成、各模組有哪些參數 |
| **E125** | CMD | 共用元數據 | EDA 介面的元數據基礎——資料型態、單位、有效範圍的描述方式 |
| **E128** | EDA Trace | 時序數據擷取 | 定義如何訂閱和接收高頻時序數據（Trace Data），是 FDC 的主要數據來源 |
| **E132** | EDG | 數據收集觸發 | 定義如何觸發數據收集——基於事件、基於時間、基於條件 |
| **E134** | DCP | 數據收集計畫 | 定義數據收集的計畫和配方——要收什麼、多頻繁、收多久 |
| **E147** | ESD | 設備自描述 | 設備自報家門——告訴系統自己有哪些參數可以收集 |
| **E157** | — | 模組製程追蹤 | 把製程數據與特定模組/腔體綁定 |
| **E164** | — | EDA 共用服務 | EDA 標準間的共用基礎服務 |

### 設備安全與設施標準

| 標準 | 名稱 | 範圍 |
|------|------|------|
| **S2** | 設備安全指南 | 設備的環境、健康與安全要求總綱。新設備進廠必過的關卡 |
| **S8** | 人因工程 | 操作介面、維護通道、人機互動的工效學（Ergonomics）要求 |
| **S22** | 電氣設計 | 設備電氣安全設計指南——接地、絕緣、急停 |
| **S23** | 節能環保 | 能源、用水、排氣、廢棄物的減量設計要求 |

### 資安標準

| 標準 | 名稱 | 實務重點 |
|------|------|---------|
| **E187** | 晶圓廠設備資安 | 設備供應商必須滿足的資安基線。涵蓋作業系統、網路、帳號、日誌四大面向。**台積電帶頭推動，已成業界強制門檻** |
| **E188** | 無惡意軟體設備交付 | 設備進廠時必須通過惡意軟體掃描。定義掃描流程和合格標準 |

> 資安標準的詳細實施指引，參見 [safety-security.md](safety-security.md)。

## GEM / GEM300 實務

GEM 是晶圓廠設備自動化的核心。理解 GEM 就是理解設備如何被主機控制。

### 四個核心狀態機

GEM 定義了四個互相關聯的狀態機（State Model）。每台設備隨時都處於這四個狀態機各自的某個狀態中。

#### 1. 通訊狀態機（Communication State Model）

```
                    ┌──────────────────┐
                    │   DISABLED       │  ← 設備啟動時的初始狀態
                    └────────┬─────────┘
                             │ 啟用通訊
                    ┌────────▼─────────┐
              ┌─────│  WAIT FOR HOST   │  ← 等待主機建立連線
              │     └────────┬─────────┘
              │              │ 收到主機回應
              │     ┌────────▼─────────┐
              │     │  COMMUNICATING   │  ← 正常通訊中
              │     └──────────────────┘
              │
              └──→ 逾時後回到 DISABLED
```

**實務重點**：通訊中斷後的重連機制——HSMS 的 T3（回覆逾時）、T5（連線分離逾時）、T6（控制逾時）設定要根據網路環境調整。預設值在高負載時可能太短。

#### 2. 控制狀態機（Control State Model）

```
  HOST-OFFLINE ←──→ HOST-ONLINE
                        │
              ┌─────────┼─────────┐
              │         │         │
           ONLINE    ONLINE    ONLINE
           LOCAL     REMOTE    LOCAL+REMOTE
              │         │
              │     可接受遠端指令
              │
          只接受本地操作
```

**實務重點**：
- 設備在「線上本地」（Online Local）模式時，主機發送的遠端指令會被拒絕
- 操作員可以在面板上切換模式——這是一個常見的自動化流程中斷來源
- 系統設計時要考慮「操作員把設備切到本地模式後忘記切回來」的情境

#### 3. 製程狀態機（Process State Model）

定義設備的加工狀態：閒置（Idle）→ 執行中（Processing）→ 完成（Complete）。E40 在此基礎上建立完整的製程作業生命週期。

#### 4. 載具狀態機（Carrier State Model，E87）

300mm 設備特有，追蹤 FOUP（前開式統一標準載具, Front Opening Unified Pod）從到達設備到離開設備的完整生命週期。

### 遠端指令流程（Remote Command）

主機對設備下達指令的典型流程：

```
主機（Host）                              設備（Equipment）
    │                                         │
    │─── S2F41 Remote Command ──────────────→│  ① 主機發送遠端指令
    │                                         │     （例如 START、STOP、ABORT）
    │←── S2F42 Acknowledge ─────────────────│  ② 設備回覆是否接受
    │                                         │     （HCACK: 0=OK, 1=拒絕, 6=權限不足）
    │                                         │
    │←── Collection Event Report ───────────│  ③ 設備狀態改變時主動通知
    │                                         │
```

**關鍵設計要點**：
- S2F42 的 HCACK（Host Command Acknowledge）代碼要正確處理——特別是代碼 1（指令不存在）和代碼 6（未授權）
- 指令是非同步的——發出指令後要靠事件報告（Collection Event）確認執行結果
- 不要用輪詢（Polling）代替事件驅動——在高負載廠區這會拖垮整個通訊

### 收集事件與變數報告（CEID / VID）

GEM 的數據報告機制：

- **收集事件**（Collection Event, CE）：設備狀態變化時觸發（例如製程開始、製程結束、警報觸發）
- **變數**（Variable）：狀態變數（SV，唯讀）和設備常數（EC，可讀寫）
- **報告**（Report）：把一組變數綁在一起
- **連結**（Link）：把報告綁到事件——當事件觸發時，自動送出綁定的報告

設定順序：定義變數 → 定義報告（包含哪些變數）→ 連結報告到事件 → 啟用事件。

### 警報管理（Alarm Management）

| 層級 | GEM 訊息 | 意義 | 處理方式 |
|------|---------|------|---------|
| 告警設置 | S5F1 | 警報啟動 | 記錄、顯示、等待評估 |
| 告警解除 | S5F1（清除碼） | 警報恢復 | 更新狀態、記錄持續時間 |
| 告警清單 | S5F5/F6 | 查詢目前所有啟動中的警報 | 用於畫面顯示和狀態同步 |

**實務重點**：GEM 的警報和 FDC 的故障不是同一件事。GEM 警報是設備自報的，FDC 故障是由外部系統根據數據分析判定的。兩者要同時管理但不能混為一談。

## EDA 數據架構

EDA（Equipment Data Acquisition）是 GEM 之外的另一條數據通道。GEM 是「設備推送什麼你就收什麼」，EDA 是「你要什麼就去訂閱什麼」。

### 為什麼需要 EDA？GEM 不夠用嗎？

| 面向 | GEM（E30） | EDA（E120 系列） |
|------|-----------|-----------------|
| 數據模式 | 事件驅動，設備推送 | 訂閱模式，客戶端拉取 |
| 數據頻率 | 低到中（秒級） | 高頻（毫秒級，可達 10ms） |
| 取樣彈性 | 設備商預定義的事件和報告 | 使用者自定義採集計畫 |
| 數據量 | 適中 | 巨大（每台設備每天數 GB） |
| 主要用途 | 設備控制、批次追蹤 | FDC、APC、VM、製程工程分析 |
| 對主機負擔 | 低 | 需要專門的數據基礎建設 |

**結論**：GEM 管「控制」，EDA 管「數據」。兩者互補，不是替代關係。

### EDA 元數據層級

```
Equipment（設備）
  └── Module（模組，例如腔體 Chamber）
        └── Parameter（參數，例如溫度、壓力、流量）
              ├── 屬性：名稱、型態、單位、取樣範圍
              └── 值：時間戳記 + 數值
```

E120 定義這個層級結構，E125 定義各層級的元數據格式，E147 讓設備能「自描述」這個結構。

### 數據收集計畫（Data Collection Plan, DCP）

DCP 定義「收什麼、怎麼收、收多少」：

| DCP 元素 | 說明 | 範例 |
|---------|------|------|
| 觸發條件（Trigger） | 何時開始收集 | 製程開始（Process Start） |
| 參數清單（Parameters） | 收集哪些參數 | 腔體溫度、RF 功率、氣體流量 |
| 取樣頻率（Sample Rate） | 多頻繁取一筆 | 每 100ms |
| 持續時間（Duration） | 收多久 | 整個製程步驟期間 |
| 摘要規則（Summary） | 收集完後如何彙總 | 平均值、標準差、最大值、最小值 |

### 時序數據 vs 摘要數據

- **時序數據**（Trace Data, E128）：高頻原始數據，用於 FDC 即時監控和製程工程分析
- **摘要數據**（Summary Data）：每個製程步驟或製程作業結束後的統計值，用於 APC 回饋和良率追蹤

**實務選擇**：全廠所有設備全收時序數據在技術上可行，但儲存和網路成本驚人。常見做法是——關鍵設備和關鍵參數收時序數據，其餘收摘要數據。

## 先進製程控制三支柱

先進製程控制（Advanced Process Control, APC）是晶圓廠維持良率的核心工程能力。三根支柱缺一不可。

### 支柱一：故障偵測與分類（Fault Detection & Classification, FDC）

FDC 負責即時監控製程數據，偵測異常並分類。

#### 單變量 vs 多變量方法

| 方法 | 原理 | 適用場景 | 限制 |
|------|------|---------|------|
| 單變量（Univariate） | 每個參數獨立設上下限 | 28nm 以上成熟製程，參數間相關性低 | 無法偵測「每個參數都正常但組合起來不正常」的故障 |
| 多變量（Multivariate） | 分析多參數之間的相關結構 | 14nm 以下先進製程，**必須使用** | 需要足夠的正常數據建立基線模型，模型維護成本高 |

**為什麼先進製程需要多變量？** 以蝕刻（Etch）製程為例：腔體壓力、RF 功率、氣體流量三者之間有耦合關係。壓力稍微高一點、同時功率稍微低一點，各自都在規格內，但組合起來蝕刻速率就偏了。單變量 FDC 抓不到這種故障。

#### FDC 常用技術

| 技術 | 原理（白話） | 適用情境 |
|------|------------|---------|
| 主成分分析（PCA） | 把多個參數壓縮成幾個「主要方向」，看數據有沒有偏離正常方向 | 多參數製程的整體健康監控 |
| 偏最小平方法（PLS） | 找出「哪些參數組合最影響品質」的關係 | 直接連結製程參數和品質指標 |
| 馬氏距離（Mahalanobis Distance） | 考慮參數間相關性的「偏離程度」量尺 | 異常偵測門檻設定 |
| 支撐向量機（SVM） | 在高維空間畫一條「正常/異常」的分界線 | 故障分類 |

#### 警報、故障、偏移——搞清楚區別

| 術語 | 定義 | 嚴重程度 | 處理方式 |
|------|------|---------|---------|
| 警報（Alarm） | 設備自報的異常狀態 | 依設備商定義 | 操作員評估、記錄 |
| 故障（Fault） | FDC 系統判定的製程異常 | 依 FDC 模型定義 | 可能觸發設備鎖機（Tool Inhibit） |
| 偏移（Excursion） | 品質指標超出規格的事件 | 高——可能影響良率 | 啟動偏移管理流程，追溯受影響晶圓 |

### 支柱二：逐批控制（Run-to-Run Control, R2R）

R2R 在每次加工之間調整配方參數，補償製程漂移。

#### 指數加權移動平均控制器（EWMA Controller）

EWMA 是 R2R 的主力工具。白話解釋：

> 想像你每天量體重。今天的數字和過去一段時間的平均比起來，如果偏了，你就調整一下飲食。但你不會只看今天——你會綜合最近幾天的趨勢。EWMA 就是這個邏輯：用加權平均的方式把「最近的觀察值」和「歷史趨勢」結合起來，算出下一次應該調整多少。

**控制公式核心概念**：

- **預測值** = λ × 最新量測值 + (1-λ) × 上次預測值
- **λ（權重因子）** ：介於 0 到 1 之間。λ 越大，對最新數據越敏感（反應快但容易震盪）；λ 越小，越平滑（穩定但反應慢）
- **典型 λ 值**：0.3-0.5，需根據製程特性調整

#### R2R 的兩種模式

| 模式 | 資料來源 | 反應速度 | 常見應用 |
|------|---------|---------|---------|
| 回饋控制（Feedback） | 上一批的量測結果 | 慢（要等量測完成） | 蝕刻深度、薄膜厚度控制 |
| 前饋控制（Feedforward） | 上一站的量測數據 | 快（不用等本站結果） | 微影曝光劑量補償、化學機械研磨（CMP）厚度補償 |

**最佳實務**：回饋加前饋組合使用。前饋處理已知的批次間差異（例如前站薄膜厚度偏差），回饋處理本站的漂移。

#### 典型應用場景

| 製程 | 控制參數 | 目標品質指標 |
|------|---------|------------|
| 微影（Litho） | 曝光劑量、對焦偏移 | 圖案尺寸（CD）、套準精度（Overlay） |
| 蝕刻（Etch） | 蝕刻時間、RF 功率 | 蝕刻深度、蝕刻角度 |
| 化學氣相沉積（CVD） | 溫度、氣體流量、時間 | 薄膜厚度、均勻性 |
| 化學機械研磨（CMP） | 下壓力、轉速、時間 | 移除量、平坦度 |

### 支柱三：虛擬量測（Virtual Metrology, VM）

VM 用製程數據預測量測結果，減少實體量測頻率。

#### 為什麼需要 VM？

- 實體量測（Physical Metrology）耗時且昂貴——一片晶圓量測可能要 30 分鐘到數小時
- 目前大多數製程只抽檢（例如每批抽 3-5 片），其他晶圓的品質是未知的
- VM 讓每片晶圓都有「預測品質」，大幅提升品質覆蓋率

#### VM 的誠實現狀

| 面向 | 現實 |
|------|------|
| 數據品質要求 | **極高**。輸入特徵（製程參數）要和實體量測結果精確對齊。時間戳偏差、感測器漂移、數據缺失都會嚴重影響模型效果 |
| 模型維護 | **持續性工作**。製程漂移、設備保養（PM）後的特性變化、新配方導入都需要重新校準模型 |
| 適用範圍 | 成熟且穩定的製程效果最好。製程變動大或剛開發的製程，VM 的預測信心不足 |
| 投資回報 | 量測機台昂貴且產能有限的製程回報最高（例如關鍵尺寸量測、膜厚量測） |
| 信任建立 | 需要長時間的平行驗證（VM 預測值 vs 實體量測值），才能說服製程工程師信任 VM 結果 |

> ⚠️ VM 不是「裝了就忘」的系統。如果沒有持續的模型監控和再訓練機制，VM 的預測精度會隨時間衰退。這是很多 VM 專案最終失敗的主因。

## 良率管理

良率（Yield）是晶圓廠的終極指標。所有系統建設最終都要回答：「這對良率有什麼幫助？」

### 製程能力指標

| 指標 | 公式概念 | 判讀標準 | 意義 |
|------|---------|---------|------|
| Cp | 規格寬度 / 製程分散寬度 | ≥1.33 合格，≥1.67 優良 | 製程「有沒有能力」在規格內——只看分散程度，不管偏不偏 |
| Cpk | 考慮偏移的 Cp | ≥1.33 合格，≥1.67 優良 | 製程「實際上」在不在規格內——同時看分散和偏移 |
| Cp 高但 Cpk 低 | — | 需要調整 | 製程精度夠但偏了——調回中心就好 |
| Cp 和 Cpk 都低 | — | 需要改善 | 製程能力本身不足——需要找出變異來源 |

> 關於 SPC 基礎和六標準差方法論的完整說明，參見 [quality-reliability.md](quality-reliability.md)。

### 晶圓圖異常辨識（Wafer Map Pattern Recognition）

晶圓圖（Wafer Map）上的不良晶粒分布模式是良率診斷的關鍵線索：

| 模式（Pattern） | 可能原因 | 診斷方向 |
|----------------|---------|---------|
| 邊緣集中（Edge） | 蝕刻均勻性、CVD 邊緣覆蓋不足 | 腔體均勻性調校 |
| 環形（Ring） | 旋轉類製程（CMP、旋塗）的不均勻 | 轉速、壓力分布 |
| 刮痕（Scratch） | CMP 研磨墊損傷、搬運刮傷 | 機械檢查 |
| 隨機分散（Random） | 微粒汙染（Particle） | 潔淨度管控 |
| 區塊集中（Cluster） | 光罩缺陷（Reticle Defect） | 光罩檢查 |
| 半圓/扇形 | 離子佈植角度偏差 | 離子佈植機校正 |
| 同心圓 | 熱製程溫度梯度 | 加熱器分區調校 |

**實務提醒**：現代晶圓圖辨識已廣泛使用卷積神經網路（CNN）自動分類。但自動分類的結果仍需要製程工程師確認——模型可能把兩種外觀相似但成因不同的模式搞混。

### 良率損失的柏拉圖分析（Yield Loss Pareto）

良率管理的標準動作：

1. **蒐集數據**：依製程站、設備、腔體、時段彙整良率數據
2. **分類損失來源**：系統性（Systematic）vs 隨機性（Random）、製程相關 vs 設備相關
3. **排序**：按影響量排柏拉圖——通常前 3-5 個原因佔 80% 的良率損失
4. **追溯**：從不良晶粒回推到具體的製程步驟、設備、時間區間
5. **改善與驗證**：實施改善、確認良率回升、標準化

### 偏移管理流程（Excursion Management）

當品質指標超出規格時的標準處理流程：

```
偵測到偏移
    │
    ├── ① 鎖機（Tool Inhibit）— 立即停止可疑設備
    │
    ├── ② 影響範圍評估（Lot Disposition）
    │       ├── 哪些批次受影響？
    │       ├── 這些批次目前在哪裡？（在線？已出貨？）
    │       └── 影響程度多大？（全批報廢 vs 降規使用 vs 安全放行）
    │
    ├── ③ 根因分析（Root Cause Analysis）
    │       ├── 時間線回溯
    │       ├── 設備/製程變更記錄比對
    │       └── FDC 數據分析
    │
    └── ④ 改善與預防
            ├── 短期：修正製程參數或設備
            ├── 中期：更新 FDC 規則
            └── 長期：修改設計規則或製程流程
```

## EES 與遠端診斷

設備工程系統（Equipment Engineering System, EES）和遠端診斷（e-Diagnostics）是維持設備稼動率的基礎建設。

### EES 架構

```
                   ┌─────────────────┐
                   │  EES 中央伺服器  │
                   │（數據彙整、分析） │
                   └────────┬────────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
     ┌────────▼───┐  ┌─────▼─────┐  ┌───▼────────┐
     │ FDC 伺服器  │  │ R2R 伺服器│  │ VM 伺服器  │
     └────────┬───┘  └─────┬─────┘  └───┬────────┘
              │             │             │
              └─────────────┼─────────────┘
                            │
                   ┌────────▼────────┐
                   │  EDA 數據收集層  │
                   └────────┬────────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
         設備 A          設備 B         設備 C
```

### 預測性維護在晶圓廠

| 維護策略 | 觸發條件 | 風險 | 適用場景 |
|---------|---------|------|---------|
| 時間基準（TBM） | 固定週期（例如每 3000 片晶圓） | 可能過早或過晚 | 低風險消耗件（O-ring、濾網） |
| 狀態基準（CBM） | 感測器數據超過門檻 | 依賴感測器品質 | 可監控的機械零件（軸承、幫浦） |
| 預測性（PdM） | 模型預測剩餘壽命 | 模型失準風險 | 昂貴且影響產能的零件（腔體零件、光源） |

**實務建議**：不要一開始就追求全廠預測性維護。先從幾台瓶頸設備的關鍵零件開始，建立資料管線和模型，驗證投資回報後再擴展。

## 常見踩坑

### GEM 狀態機違規

**症狀**：主機發送指令被設備拒絕，或設備狀態和主機認知不一致。

**根因**：沒有正確追蹤設備的控制狀態機。例如設備處於「線上本地」（Online Local）模式時送遠端指令，或在設備忙碌時送啟動指令。

**解法**：
- 主機端必須維護每台設備的完整狀態模型
- 在發送指令前檢查狀態是否允許
- 處理好狀態轉移過程中的競態條件（Race Condition）

### EDA 數據爆炸

**症狀**：EDA 儲存空間快速耗盡，網路頻寬飽和，數據查詢變慢。

**根因**：DCP 設定太貪心——所有設備、所有參數、最高取樣頻率。

**解法**：
- 區分「必須即時收集」和「事後調查時再拉」的數據
- 關鍵設備/關鍵參數用高頻取樣，其餘用摘要數據
- 建立數據生命週期管理：熱數據（即時分析）→ 溫數據（近期查詢）→ 冷數據（長期歸檔）
- 典型數據量參考：一台先進製程設備每天約 2-10 GB 時序數據。一座 300mm 廠有數百台設備

### FDC 誤報疲勞（False Alarm Fatigue）

**症狀**：工程師每天收到數百到數千筆 FDC 告警，逐漸忽略所有告警。

**根因**：
- FDC 模型的正常基線建立不良（訓練數據不夠乾淨或不夠多）
- 規格限設得太緊
- 沒有區分「立即處理」和「觀察追蹤」的告警等級

**解法**：
- 告警分級：紅燈（立即處理，設備鎖機）、黃燈（儘速處理）、資訊（記錄觀察）
- 定期回顧誤報率——目標是真陽性率（Precision）至少 80% 以上
- FDC 模型需要隨製程變化持續更新，不是建好就不管

### R2R 控制器震盪

**症狀**：被控參數在目標值上下來回擺盪，不收斂。

**根因**：
- EWMA 的 λ 值設太大（對雜訊過度反應）
- 製程增益（Process Gain）估計不準確——控制器以為調 1 個單位會改變 0.5，實際上改變了 2
- 量測延遲太長，控制器來不及看到自己上一次調整的效果就又調了

**解法**：
- 降低 λ 值（常見調整方向：0.5 → 0.3 → 0.2）
- 重新估計製程增益，必要時做設計實驗（DOE）
- 如果量測延遲超過一個批次間隔，考慮加入前饋控制補償
- 設定調整量的上下限（Clamp），防止單次過度修正

### 設備保養後的系統衝擊

**症狀**：設備做完預防保養（PM）後，FDC 大量告警、R2R 控制器偏離、VM 預測失準。

**根因**：PM 改變了設備特性（例如更換腔體零件後的蝕刻速率改變），但各系統的基線/模型沒有同步更新。

**解法**：
- 建立「PM 後回復」的標準作業程序，包含：
  1. FDC 基線重置或進入學習模式
  2. R2R 控制器重置到開環（Open Loop）跑幾批建立新基線
  3. VM 模型標記為「待重新校準」，暫時回到實體量測
- 在 MES/EES 系統中標記 PM 事件，讓下游系統自動觸發回復流程

### SEMI E187 合規的隱性成本

**症狀**：設備供應商說「我們符合 E187」，但實際整合時問題一堆。

**根因**：E187 合規有不同層次的解讀——「作業系統有白名單」和「能和廠區 SOC 完整整合」是兩回事。

**解法**：
- 在設備採購規格書（Spec）中明確列出 E187 的具體要求，不只引用標準編號
- 要求供應商提供合規報告（Compliance Report），逐條對照
- 特別注意：帳號管理、日誌格式、網路分段、外部儲存媒體管控這四個實務落差最大的領域
- 更多資安實務，參見 [safety-security.md](safety-security.md)
