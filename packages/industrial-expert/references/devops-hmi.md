## 1. 為什麼工業需要開發維運

### 工業軟體管理的現況：一場慢性災難

在多數工業場域中，軟體管理的現況是這樣的：

- **PLC 程式碼存在隨身碟裡**：工程師離職後，沒人知道那支隨身碟在哪裡，或者控制器裡跑的版本跟隨身碟上的一不一樣
- **HMI 專案沒有版本歷史**：畫面改了什麼、誰改的、什麼時候改的，完全無從追查
- **變更在生產線上直接測試**：「先上去跑看看」是常態，測試環境是生產環境
- **部署靠人工操作**：把專案檔複製到控制器，靠的是工程師的記憶和手動操作

這些問題在資訊技術（Information Technology, IT）領域早就有成熟的解法，統稱為開發維運（Development and Operations, DevOps）。但工業場域的營運技術（Operational Technology, OT）有其特殊限制，不能照搬 IT 的做法。

### OT 環境的特殊限制

| 限制 | 說明 | 對開發維運的影響 |
|------|------|----------------|
| 即時性要求 | 控制迴路的掃描週期以毫秒計算 | 部署不能中斷即時控制 |
| 可用度要求 | 製程通常要求 99.5% 以上可用度 | 停機窗口（Maintenance Window）稀少且寶貴 |
| 網路隔離 | OT 網路通常與 IT 網路隔離（Air-Gap 或防火牆） | 自動化部署管線難以跨越網路邊界 |
| 專有格式 | 大多數 PLC/DCS 使用專有二進制專案格式 | 傳統版本控制工具無法直接處理 |
| 法規要求 | 變更必須經過正式核准流程 | 「一鍵部署」可能違反法規，參見 [project-compliance.md](project-compliance.md) 的變更管理章節 |
| 安全考量 | 不當變更可能造成人身安全風險 | 每次部署都需要人為確認步驟 |

## 2. 工業軟體的版本控制

### 2.1 可程式控制器（PLC）/ 分散式控制系統（DCS）程式碼

#### 哪些東西可以做版本控制？

| 程式語言（IEC 61131-3） | 版本控制可行性 | 說明 |
|------------------------|--------------|------|
| 結構化文字（Structured Text, ST/SCL） | 高 | 純文字檔案，可直接用 Git 追蹤差異 |
| 指令清單（Instruction List, IL） | 高 | 純文字格式，但可讀性較差 |
| 功能區塊圖（Function Block Diagram, FBD） | 中 | 可匯出為 XML，差異比對可行但不直觀 |
| 梯形圖（Ladder Diagram, LD） | 中 | 同 FBD，XML 匯出後可追蹤但難以人工審查 |
| 順序功能圖（Sequential Function Chart, SFC） | 低-中 | 結構較複雜，XML 差異比對的可讀性更差 |

#### 各平台的版本控制策略

| 平台 | 原生格式 | 版本控制方式 | 限制 |
|------|---------|------------|------|
| Siemens TIA Portal | 專有二進制（.ap17） | TIA Openness API 匯出 XML；或用第三方工具（如 versiondog） | API 需要授權，匯出/匯入耗時 |
| Rockwell Studio 5000 | 專有二進制（.ACD） | L5X 匯出（XML 格式）；或 FactoryTalk AssetCentre | L5X 檔案龐大，差異比對需專用工具 |
| CODESYS | 專有 + 可匯出 | 原生支援 SVN/Git 整合（3.5 SP17+） | 圖形語言的差異比對仍不完善 |
| Schneider EcoStruxure | 專有二進制 | 匯出為 XML 或使用 Schneider 自家版控 | 工具整合程度有限 |
| Beckhoff TwinCAT | 基於 Visual Studio | 天生與 Git 相容（.sln/.tsproj 為文字格式） | 少數組態檔為二進制 |

**務實建議**：如果你的目標只是「知道控制器裡跑的版本跟設計文件是不是同一版」，不一定需要完整的 Git 工作流。定期將專案檔（含匯出的文字格式）備份到有版本標記的資料夾，配合程式碼比對工具（如 AutoSave by MDT），已經比「存在隨身碟」好十倍。

### 2.2 HMI / SCADA 專案

| 平台 | 版本控制考量 |
|------|------------|
| Siemens WinCC（TIA 整合版） | 跟隨 TIA Portal 的版本控制策略；獨立版 WinCC 可匯出 XML |
| Rockwell FactoryTalk View | ME 版較封閉；SE 版可拆解為多個可管理的檔案 |
| Inductive Automation Ignition | **最友善**：專案可匯出為 JSON/XML，天生適合 Git；網關備份（Gateway Backup）含完整組態 |
| AVEVA（原 Wonderware） | InTouch 專案可匯出為 CSV/XML 清單 |
| GE iFIX / CIMPLICITY | 較舊的架構，版本控制主要靠檔案層級備份 |

**Ignition 是目前對開發維運最友善的 SCADA 平台**。它的專案結構（標籤、畫面、腳本）可以完全拆解為文字檔案，放進 Git 追蹤。如果你在新專案中有平台選擇權，這一點值得考慮。

### 2.3 配方/參數管理

工業系統中有大量「不是程式碼但影響行為」的配置資料：

- **配方（Recipe）**：不同產品對應不同的設定參數組合（依 ISA-88 批次控制標準管理）
- **控制參數**：PID 參數、報警門檻、計時器設定值
- **通訊組態**：OPC 標籤清單、Modbus 位址對應表

這些資料應該用參數化的方式管理（跟程式碼分離），並且有獨立的版本控制。常見的做法是用 CSV 或 JSON 格式儲存，搭配 Git 追蹤變更。

### 2.4 Git 工作流 for OT

工業軟體不需要複雜的 Git 工作流。建議採用最簡單的模型：

```
main（主線）
  ├── feature/pump-station-3-logic  （功能分支）
  ├── feature/hmi-alarm-summary     （功能分支）
  └── hotfix/level-interlock-fix    （緊急修復）
```

#### 提交訊息慣例

```
[類型] 區域: 變更摘要

類型：feat（新增功能）/ fix（修復問題）/ refactor（重構）/ docs（文件）
區域：對應製程區域或子系統名稱

範例：
[feat] 加藥系統: 新增 pH 串級控制邏輯
[fix] 冷卻水塔: 修復高液位互鎖誤觸發問題
[docs] 全廠: 更新 I/O 清單至 Rev.C
```

#### 程式碼審查（Code Review）for PLC 邏輯

PLC 程式碼的審查重點跟 IT 軟體不同：

| 審查項目 | 說明 |
|---------|------|
| 安全互鎖完整性 | 所有互鎖條件是否都已實作？是否與因果矩陣一致？ |
| 異常處理 | 感測器斷線、通訊逾時、執行器故障時的系統行為 |
| 計時器/計數器邊界 | 溢位條件、重置邏輯、運轉時間累計 |
| 掃描週期影響 | 新增的邏輯是否會導致掃描週期超限？ |
| 硬編碼值 | 是否有魔術數字（Magic Number）？應該參數化的常數是否都已提取？ |
| 命名一致性 | 變數命名是否符合專案命名規範？ |

## 3. 持續整合與持續交付 for 工業軟體

### 3.1 模擬測試

#### PLC 模擬器

| 平台 | 模擬工具 | 能做什麼 | 不能做什麼 |
|------|---------|---------|-----------|
| Siemens | PLCSim / PLCSim Advanced | 基本邏輯驗證、通訊模擬（Advanced 版） | 即時性能驗證、實體 I/O 行為 |
| Rockwell | Studio 5000 Emulate | 邏輯驗證、RSLogix 模擬 | 特殊模組（運動控制、高速計數器） |
| CODESYS | 內建模擬器 | 邏輯驗證、視覺化除錯 | 平台特定行為 |
| Beckhoff | TwinCAT XAR（模擬模式） | 完整運行環境模擬 | 實體 EtherCAT 時序 |

#### 自動化測試腳本

可以在模擬環境中自動執行的測試：

- **單元測試**：個別功能區塊的輸入/輸出驗證
- **序列測試**：自動執行啟動/停機/切換產品等操作序列，驗證狀態轉移
- **迴歸測試**：每次變更後自動重跑關鍵測試，確保既有功能未受影響
- **邊界測試**：類比輸入在量程上下限、計時器在最大值等邊界條件

### 3.2 部署管線

工業軟體的部署管線跟 IT 的差異：

```
原始碼（Git）
  → 建構/編譯（自動）
  → 模擬測試（自動）
  → 測試報告產生（自動）
  ─── 核准閘門（人工）───
  → 部署到測試控制器（半自動）
  → 現場確認測試（人工）
  ─── 核准閘門（人工）───
  → 部署到生產控制器（人工 + 排定停機窗口）
  → 運轉確認（人工）
```

**兩個人工核准閘門不可省略**。這不是 IT 的持續部署（Continuous Deployment），而是持續交付（Continuous Delivery）——程式碼隨時可以部署，但部署的決定由人來做。

### 3.3 限制與現實

在推動工業開發維運時，必須認清幾個現實：

1. **文化障礙比技術障礙更大**：OT 工程師通常不熟悉 Git，需要教育訓練和耐心
2. **投資報酬率難以量化**：「避免了一次停機事故」很難用數字呈現給管理層
3. **工具鏈不成熟**：IT 有完整的 DevOps 工具生態，OT 的工具選擇有限
4. **不要追求完美**：從最簡單的地方開始——先做好版本控制，再談自動化測試，最後才考慮持續交付

## 4. 基礎設施即程式碼 for 邊緣運算

### 4.1 容器化（Containerization）

#### 什麼時候該用容器？

| 適用場景 | 不適用場景 |
|---------|-----------|
| 邊緣分析應用（資料前處理、異常偵測模型） | 即時控制邏輯（PLC 程式） |
| 協定轉換閘道（Protocol Gateway） | 需要確定性即時（Deterministic Real-Time）的應用 |
| 資料蒐集代理程式（Data Collection Agent） | 直接操作工業匯流排（Fieldbus）的應用 |
| 邊緣視覺化（本地儀表板） | 安全儀表功能（SIF） |
| 機器學習推論（ML Inference） | 需要直接存取實體 I/O 的應用 |

#### 容器化的實務考量

- **映像大小**：邊緣設備的儲存空間有限，映像（Image）要盡量精簡
- **資源限制**：設定記憶體和 CPU 上限，避免容器吃掉所有資源影響其他服務
- **持久化儲存**：時序資料庫（Time-Series Database）和組態檔必須掛載到主機磁碟
- **網路模式**：工業協定可能需要 host 網路模式才能正常運作（如 Multicast）
- **重啟策略**：設定為自動重啟（`restart: always`），邊緣設備斷電重開後服務必須自動恢復

### 4.2 邊緣編排（Edge Orchestration）

| 工具 | 適用場景 | 資源需求 | 複雜度 |
|------|---------|---------|--------|
| Docker Compose | 單節點、少量容器（≤10） | 最低 | 低 |
| K3s | 多節點邊緣叢集、需要服務發現 | 512MB RAM 起 | 中 |
| MicroK8s | 開發/測試、單節點生產 | 540MB RAM 起 | 中 |
| KubeEdge | 雲端管理大量邊緣節點 | 中等 | 高 |
| Azure IoT Edge | 與 Azure 生態整合 | 中等 | 中 |
| AWS Greengrass | 與 AWS 生態整合 | 中等 | 中 |

**務實建議**：如果邊緣節點只有 5-10 個容器，Docker Compose 就夠了。不要因為「潮流」而導入 Kubernetes——在只有三台邊緣閘道（Edge Gateway）的場景，K8s 的管理成本遠大於收益。

### 4.3 配置管理

OT 基礎設施中有大量需要管理的組態：

- **網路交換器（Network Switch）**：VLAN 設定、埠口安全（Port Security）、生成樹協定（Spanning Tree Protocol, STP）
- **防火牆規則**：OT/IT 網路邊界的存取控制清單（Access Control List, ACL）
- **邊緣伺服器**：作業系統組態、服務設定、憑證管理

用基礎設施即程式碼（Infrastructure as Code, IaC）工具來管理這些組態：

| 工具 | OT 適用場景 | 注意事項 |
|------|------------|---------|
| Ansible | 邊緣伺服器組態、網路設備設定 | 不需安裝代理程式（Agentless），適合 OT 環境 |
| Terraform | 雲端/虛擬化基礎設施 | 主要用於 IT 側和混合雲架構 |
| Git + 腳本 | 防火牆規則、交換器組態備份 | 最低門檻的起步方式 |

**安全提醒**：OT 基礎設施的組態管理必須與資安生命週期整合，參見 [safety-security.md](safety-security.md) 的 IEC 62443 區域與導管模型。

## 5. 可觀測性 for 營運技術

### 5.1 工業場域的三支柱

可觀測性（Observability）在 IT 領域有三支柱：指標（Metrics）、日誌（Logs）、追蹤（Traces）。工業場域的對應概念：

| IT 概念 | OT 對應 | 資料來源 | 用途 |
|--------|---------|---------|------|
| 指標 | 製程資料 | 感測器、PLC 暫存器、歷史資料庫 | 製程監控、趨勢分析 |
| 日誌 | 系統事件 | PLC 診斷、SCADA 事件記錄、作業系統日誌 | 故障排查、稽核軌跡 |
| 追蹤 | 通訊流程 | 網路封包擷取、OPC UA 訂閱診斷 | 通訊問題排查、效能瓶頸 |

### 5.2 監控工具選型

| 架構組合 | 優勢 | 劣勢 | 適用場景 |
|---------|------|------|---------|
| Grafana + InfluxDB | 時序資料原生支援、查詢效能好 | InfluxDB 叢集版需商業授權 | 中小型場域、時序資料為主 |
| Grafana + Prometheus | 拉取模式（Pull-based）、成熟的警報規則 | 不適合高頻製程資料（>1Hz） | 基礎設施監控、邊緣設備健康 |
| Grafana + TimescaleDB | 結合關聯式資料庫能力與時序效能 | 需要 PostgreSQL 維運經驗 | 需要複雜查詢和關聯分析 |
| 商業歷史資料庫 + 原生工具 | 與 DCS/SCADA 深度整合、法規合規 | 授權費高、擴展性受限 | 大型場域、嚴格法規要求 |

#### 儀表板設計原則

工業監控儀表板的設計應遵循 ISA-101 的原則（後續章節詳述），核心要點：

- **一個儀表板回答一個問題**：不要把所有指標塞進同一個畫面
- **預設顯示正常狀態，異常狀態用顏色突顯**
- **趨勢圖的時間軸要對應操作節奏**：如果操作員每小時巡檢一次，預設顯示 2 小時區間

### 5.3 異常偵測 vs 警報管理

| 項目 | 傳統警報 | 異常偵測 |
|------|---------|---------|
| 觸發方式 | 固定門檻值（High/Low/HiHi/LoLo） | 統計模型、機器學習 |
| 反應速度 | 即時（毫秒級） | 準即時（秒到分鐘級） |
| 可解釋性 | 高（超過某值就報警） | 中到低（模型判定「異常」） |
| 維護需求 | 門檻值需定期校準 | 模型需定期重訓練 |
| 法規接受度 | 高（已被廣泛接受） | 發展中（需額外驗證） |

**務實建議**：異常偵測不能取代傳統警報。安全相關的警報必須使用固定門檻值（法規要求），異常偵測作為「早期預警」的補充層，幫助操作員在問題惡化到觸發警報之前就察覺。

## 6. ISA-101 高效能 HMI 設計

### 為什麼傳統 HMI 設計有問題？

大多數工業場域的 HMI 畫面長這樣：

- **色彩過度使用**：正常狀態下整個畫面五顏六色，操作員無法分辨「什麼是需要注意的」
- **資訊過載**：一個畫面上放 200 個標籤值，操作員根本看不完
- **擬真化設計**：花大量心力把管線畫得像照片，但這些視覺元素對操作決策毫無幫助
- **不一致的互動模式**：每個畫面的操作方式不同，操作員需要記住大量特例
- **導航結構不清楚**：操作員找不到需要的資訊，或者需要點擊七八次才能到達目標畫面

這不是美學問題。畫面設計不良直接影響操作員的態勢感知（Situation Awareness），而態勢感知的喪失是工業事故的主要原因之一。

### ISA-101 核心原則

#### 態勢感知的三個層次（Endsley Model）

| 層次 | 描述 | HMI 如何支援 |
|------|------|-------------|
| 第一層：感知 | 操作員能看到當前狀態 | 清楚呈現關鍵參數的即時值 |
| 第二層：理解 | 操作員能理解狀態的含義 | 用趨勢、顏色變化呈現「跟正常比起來怎麼樣」 |
| 第三層：預測 | 操作員能預判下一步會發生什麼 | 趨勢外推、預測模型、操作提示 |

大多數傳統 HMI 只支援到第一層。高效能 HMI（High Performance HMI）的目標是同時支援三個層次。

#### HMI 的四個層級

ISA-101 定義了四個層級的 HMI 畫面，從全廠總覽到設備診斷：

| 層級 | 名稱 | 內容 | 使用頻率 |
|------|------|------|---------|
| L1 | 全廠總覽 | 關鍵績效指標、各區域狀態摘要、異常區域標示 | 持續監看 |
| L2 | 製程區域 | 製程流程圖、控制迴路狀態、趨勢圖 | 頻繁切換 |
| L3 | 設備單元 | 個別設備的詳細操作畫面、設定值調整、手動操作 | 按需進入 |
| L4 | 診斷資訊 | 設備診斷、通訊狀態、原始資料、維護資訊 | 故障排查時 |

**L1 是最關鍵的畫面**。操作員 80% 的時間應該在 L1 上就能掌握全廠狀態。如果操作員必須不停地在 L2/L3 畫面之間切換才能了解狀況，那 L1 的設計就失敗了。

#### 具體的工廠範例

以一座水處理廠為例：

- **L1 全廠總覽**：一個畫面顯示進水水質、各處理單元的處理效率（用模擬棒圖，綠色區域表示正常範圍）、出水水質、藥劑庫存量。不畫管線，不畫設備外形。
- **L2 加藥系統**：加藥系統的控制迴路狀態，pH 值趨勢（過去 2 小時，含設定值和控制上下限），加藥泵運轉狀態，藥劑流量。
- **L3 加藥泵操作**：單台加藥泵的手自動切換、轉速設定、運轉時數、振動值、密封水壓力。
- **L4 加藥泵診斷**：變頻器錯誤碼、通訊診斷、歷史故障紀錄、維護排程。

### 色彩規範

**最重要的原則：灰色為預設，顏色只用在例外。**

| 顏色 | 用途 | 禁止用途 |
|------|------|---------|
| 灰色（深淺變化） | 正常狀態的管線、設備、背景 | — |
| 綠色 | 運轉中、正常狀態確認 | 裝飾、背景 |
| 紅色 | 故障、緊急停車、高優先警報 | 正常運轉狀態 |
| 琥珀色（Amber） | 警告、需要注意但非緊急 | 正常運轉狀態 |
| 藍色 | 資訊提示、導航元素 | 製程狀態表示 |
| 白色 | 文字、數值顯示 | 背景（太亮會造成眼睛疲勞） |

**背景色**：中灰色（約 RGB 190, 190, 190）。不用黑色（反差太強，長時間觀看會疲勞），不用白色（同理），不用深藍色（降低文字可讀性）。

### 導航設計

- **階層式導航**：廠區 → 區域 → 單元 → 設備，每一層都能清楚知道自己在哪裡
- **麵包屑導航（Breadcrumb Navigation）**：永遠顯示當前位置路徑，如「水處理廠 > 加藥系統 > 1 號加藥泵」
- **警報摘要永遠可見**：不管在哪個畫面，當前未確認的高優先警報數量必須始終顯示
- **一鍵回家**：任何畫面都能一次點擊回到 L1 全廠總覽

### 高效能 HMI 設計流程

1. **使用者需求分析**：訪談操作員——他們需要什麼資訊做什麼決定？
2. **資訊架構設計**：定義四個層級的畫面結構和導航邏輯
3. **線框圖（Wireframe）**：先用灰階設計，確認資訊佈局
4. **風格指南（Style Guide）**：定義色彩、字型、控制元件的統一規範
5. **原型製作與使用性測試**：讓操作員實際操作原型，收集回饋
6. **實作與驗證**：依風格指南實作，驗證與線框圖的一致性

## 7. ISA-18.2 警報管理

### 為什麼警報管理是生死攸關的事？

警報氾濫（Alarm Flood）不是「系統跳太多訊息」那麼簡單。當操作員每分鐘收到十幾個警報，他的認知資源會被耗盡，最終開始忽略所有警報——包括真正重要的那些。

歷史上的教訓：

- **德州城煉油廠爆炸（Texas City, 2005）**：事故前的警報氾濫導致操作員未能察覺關鍵異常，15 人死亡
- **邦斯菲爾德油庫爆炸（Buncefield, 2005）**：液位高高警報被忽略（因為站控警報系統長期存在大量無效警報），造成英國和平時期最大爆炸事故

**每一個「無所謂」的假警報，都在消耗操作員對「真正重要」警報的注意力。**

### 7.1 警報生命週期

ISA-18.2 定義了警報管理的完整生命週期：

```
識別 → 合理化 → 設計 → 實作 → 監控 → 變更管理
  ↑                                       |
  └───────────── 持續改善 ←──────────────┘
```

| 階段 | 關鍵活動 | 交付物 |
|------|---------|--------|
| 識別（Identification） | 從製程危害分析（PHA）和操作經驗識別需要的警報 | 初始警報清單 |
| 合理化（Rationalization） | 為每個警報定義目的、優先等級、操作員應對程序 | 警報合理化工作表、主警報資料庫（Master Alarm Database） |
| 設計（Design） | 設定觸發條件、延遲時間、死區（Deadband）、抑制邏輯 | 警報設計規格 |
| 實作（Implementation） | 在控制系統中配置警報 | 完成配置的警報系統 |
| 監控（Monitoring） | 追蹤警報績效指標 | 定期績效報告 |
| 變更管理（MOC） | 任何警報變更都走正式變更流程 | 變更紀錄 |

### 7.2 關鍵績效指標

| 指標 | 目標值（EEMUA 191） | 典型現況 | 說明 |
|------|-------------------|---------|------|
| 每小時每位操作員的警報數 | ≤ 6 | 30-100+ | **這是最重要的單一指標** |
| 常駐警報（Standing Alarm）數 | ≤ 5 | 20-50+ | 持續處於啟動狀態超過 24 小時的警報 |
| 聒噪警報（Chattering Alarm）比例 | < 1% | 5-15% | 在短時間內反覆觸發/恢復的警報 |
| 十分鐘內超過 10 個警報的洪峰次數 | 每週 < 5 次 | 每天數十次 | 警報洪峰會壓垮操作員的認知能力 |
| 操作員回應率 | > 80% | 30-50% | 未被回應的警報等於不存在 |

**「每小時 6 個警報」這個數字是怎麼來的？** 研究顯示，操作員在正常運轉時，每 10 分鐘能處理約 1 個警報，同時維持對製程的監控。這意味著每小時約 6 個是操作員能持續、可靠地處理的上限。超過這個數字，操作員會開始取捨——而他取捨掉的可能正好是最關鍵的那一個。

### 7.3 警報合理化（Alarm Rationalization）

警報合理化是整個警報管理中最核心、也最耗時的工作。每一個警報都必須通過合理化工作表的審查：

#### 合理化工作表的關鍵欄位

| 欄位 | 內容 | 為什麼重要 |
|------|------|-----------|
| 警報用途 | 這個警報要告訴操作員什麼？ | 如果回答不出來，這個警報就不該存在 |
| 後果 | 如果不處理會怎樣？ | 決定優先等級的依據 |
| 操作員應對 | 操作員收到後應該做什麼？ | 如果沒有對應動作，這個警報就不該存在 |
| 可用時間 | 操作員有多少時間做出反應？ | 影響設計（延遲、抑制）和優先等級 |
| 優先等級 | 關鍵/高/中/低/診斷 | 基於後果嚴重度和可用時間 |

#### 優先等級的定義（基於後果嚴重度）

| 優先等級 | 後果 | 可用時間 | 佔比目標 |
|---------|------|---------|---------|
| 關鍵（Critical） | 人員傷亡或重大環境災害 | < 5 分鐘 | < 1% |
| 高（High） | 設備損壞或嚴重品質問題 | 5-30 分鐘 | ~5% |
| 中（Medium） | 製程偏離或輕微品質問題 | 30 分鐘-4 小時 | ~15% |
| 低（Low） | 需要注意但不緊急 | > 4 小時 | ~80% |

安全相關警報的設計必須與安全儀表系統（SIS）的需求一致，參見 [safety-security.md](safety-security.md) 的 IEC 61511 章節。

### 7.4 EEMUA 191

英國工程設備及材料用戶協會（Engineering Equipment and Materials Users' Association, EEMUA）出版的第 191 號指南是 ISA-18.2 的補充文件，提供更具體的績效指標（Key Performance Indicator, KPI）和標竿比較（Benchmarking）基準。

EEMUA 191 的警報系統評等：

| 指標 | 過載（Overloaded） | 反應式（Reactive） | 穩定（Stable） | 健壯（Robust） |
|------|-------------------|-------------------|---------------|---------------|
| 每小時警報數 | > 30 | 13-30 | 7-12 | ≤ 6 |
| 常駐警報比例 | > 50% | 30-50% | 10-30% | < 10% |
| 十大聒噪警報 | 每天觸發數百次 | 數十次 | 數次 | 0 |

**多數工業場域落在「過載」或「反應式」等級。** 從「過載」進步到「穩定」通常需要 12-18 個月的持續努力，包括警報合理化、系統改善、和操作文化的改變。

## 8. 常見踩坑

### PLC 程式碼沒有註解也沒有版本紀錄

**場景**：專案交付五年後，控制邏輯需要修改。打開 PLC 程式，發現沒有任何註解，變數名稱都是 `Tag001`、`Tag002`，沒有版本紀錄可以查閱修改歷史。反向工程這些邏輯花了三週，比重新寫還久。

**對策**：在專案規格中明確要求程式碼品質標準——變數命名規範、註解要求（至少標記每個功能區塊的目的和作者）、版本紀錄。把這些納入 FAT 驗收條件。交付時要求提供完整的程式原始碼和說明文件。

### 「每個標籤都配一個警報」

**場景**：系統整合商為了「完整」，把每一個量測點都配了高高/高/低/低低四個警報。一座中型水處理廠有 500 個量測點，結果就是 2000 個警報。正常運轉時每小時跳 50 個以上，操作員直接把音效關掉。

**對策**：警報不是免費的——每一個警報都有維護成本和對操作員注意力的消耗。在設計階段就應該做警報合理化，而不是全部配上去再來「調」。一個中型場域在合理化後，通常只需要原始警報數的 30-40%。

### HMI 畫面由控制工程師設計，而非使用者體驗專家

**場景**：HMI 畫面上每根管線都畫得跟 P&ID 一模一樣，設備用 3D 渲染效果，整個畫面花花綠綠。「很好看」，但操作員找不到他需要的數值，因為那個數值藏在一堆裝飾性元素之間。

**對策**：HMI 設計應該從操作員的任務需求出發，而不是從 P&ID 的外形出發。控制工程師可以定義「需要顯示什麼資訊」，但「怎麼呈現」應該遵循 ISA-101 的原則。如果團隊中沒有使用者體驗（User Experience, UX）專長，至少要讓操作員參與設計審查。

### 開發維運工具選型沒有考慮 OT 限制

**場景**：IT 部門推動全公司統一使用某個雲端持續整合（CI）平台。但 OT 網路與 IT 網路隔離（Air-Gap），控制系統的電腦無法存取雲端服務。結果是 IT 部門花了半年建置的管線在 OT 端根本無法使用。

**對策**：OT 環境的開發維運工具必須能在隔離網路中運作。優先考慮可以在本地部署（On-Premise）的方案——如 GitLab 自架版、Jenkins、或甚至只是區域網路內的檔案伺服器搭配 Git。在確認網路架構和安全政策之後再選型，而不是反過來。網路架構的考量參見 [architecture-design.md](architecture-design.md)。

### 「灰色畫面操作員不喜歡」

**場景**：導入 ISA-101 高效能 HMI 後，操作員抱怨「畫面太單調」、「看起來像壞掉了」。部分資深操作員甚至要求改回舊版。

**對策**：這是預期中的阻力。高效能 HMI 的「灰色風格」需要教育訓練來說明設計理由。有效的做法是：先在一個非關鍵區域試行，讓操作員使用 2-4 週後再收集回饋。幾乎所有案例中，操作員在適應期後都會偏好新設計——因為他們確實能更快發現異常。但關鍵是要有這段適應期，不能一次全廠切換。

### 警報合理化做完就放著不管

**場景**：花了六個月做完警報合理化，警報數量從每小時 60 個降到 8 個。兩年後回來看，又回到每小時 40 個——因為每次擴建或修改都加了新警報，但沒有走合理化流程。

**對策**：警報管理不是一次性專案，而是持續性的管理活動。每個新增或修改的警報都必須走變更管理（MOC）流程，參見 [project-compliance.md](project-compliance.md)。至少每季產出一次警報績效報告，追蹤關鍵指標的趨勢。指派專人（或委員會）負責警報系統的持續健康。
