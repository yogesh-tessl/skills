## ISA-95 分層模型實戰解讀

### 教科書定義 vs 工廠現實

ISA-95（IEC 62264）定義了五個層級。教科書會畫出一個整齊的金字塔，但現實中這些層的邊界從來都不乾淨。

| 層級 | 教科書定義 | 工廠現實 |
|------|----------|---------|
| Level 0 — 物理過程 | 感測器、致動器 | 同教科書，但很多老設備沒有數位訊號輸出 |
| Level 1 — 基礎控制 | PLC、DCS、安全控制器 | 品牌混雜（Siemens + Mitsubishi + Rockwell 共存是常態） |
| Level 2 — 監控 | SCADA、HMI | 常與 Level 3 混在一起，很多 SCADA 順便做了一半的 MES 功能 |
| Level 3 — 製造執行 | MES、批次管理 | **痛點集中區**：客製化最多、介面最亂、升級最困難 |
| Level 4 — 企業系統 | ERP、PLM、SCM | SAP/Oracle 等大系統，改動成本極高，通常是「你配合它」 |

### Level 3 為什麼是最大痛點？

Level 3（製造執行層，Manufacturing Execution System, MES）是「OT 世界」和「IT 世界」的交界面。痛點的根源：

1. **語言不通**：Level 1-2 說的是「標籤（Tag）」、「暫存器（Register）」、「掃描週期（Scan Cycle）」；Level 4 說的是「工單」、「物料」、「成本中心」。MES 要當翻譯官，但翻譯規則每家工廠都不一樣。

2. **客製化陷阱**：MES 廠商號稱「開箱即用」，但實務上 60-80% 的功能需要客製。客製化越深，升級越難，最終變成一個誰都不敢動的黑箱。

3. **時間尺度衝突**：控制層是毫秒級、MES 是秒到分鐘級、ERP 是小時到天級。跨層的事件關聯和時間戳同步是持續性的工程難題。

### ISA-95 B2MML 資料模型

B2MML（Business to Manufacturing Markup Language）是 ISA-95 定義的 XML 資料交換格式。在以下場景有實際價值：

| 場景 | 建議 |
|------|------|
| ERP ↔ MES 工單排程整合 | 用 B2MML 的生產排程（Production Schedule）模型做為介面契約 |
| 多廠區統一報工 | 用 B2MML 的生產績效（Production Performance）模型做跨廠對齊 |
| 新 MES 評選 | 要求廠商說明其 B2MML 支援程度，做為互通性評估的基準 |
| 小型產線或單機 | 不需要 B2MML，過度工程。直接用結構化的 JSON/REST 即可 |

### 模型在哪裡崩壞？

ISA-95 的五層模型在以下場景會不適用，需要調整思維：

- **雲原生架構**：當 MES 是雲端服務（SaaS）時，Level 3 不再「位於」工廠內，傳統的網路分層假設被打破。需要重新設計安全邊界。
- **邊緣運算**：AI 推論引擎直接坐在 Level 2 甚至 Level 1 旁邊，跳過了 Level 3。資料流不再是「由下往上逐層傳遞」。
- **統一命名空間（UNS）模式**：用事件驅動架構取代逐層傳遞，所有層級的資料都發布到同一個命名空間。ISA-95 的層級概念仍用於語義分類，但不再代表資料流的物理路徑。詳見[統一命名空間](#統一命名空間)一節。

## 網路拓撲設計

### Purdue 模型（參考架構）

Purdue 模型原本是 ISA-95 的網路參考架構，將五個功能層級對應到網路區域。核心概念是**區域隔離加上受控的跨區通訊**。

| 區域 | 對應層級 | 網路特性 | 典型設備 |
|------|---------|---------|---------|
| Cell/Area Zone | Level 0-1 | 確定性、低延遲、專用協定 | PLC、DCS、安全控制器、IO 模組 |
| Site Manufacturing Zone | Level 2-3 | 工業乙太網、VLAN 隔離 | SCADA 伺服器、MES 伺服器、Historian |
| Industrial DMZ（工業非軍事區） | — | 雙重防火牆、跳板主機、代理伺服器 | 資料二極體、反向代理、檔案閘道 |
| Enterprise Zone | Level 4 | 企業 IT 網路 | ERP、CRM、企業骨幹 |

### 工業非軍事區的關鍵設計原則

工業非軍事區（Industrial DMZ, IDMZ）是 OT 和 IT 之間的緩衝帶。設計要點：

1. **雙防火牆架構**：OT 端一道牆、IT 端一道牆，IDMZ 夾在中間。禁止任何從 IT 直接到 OT 的連線穿透。
2. **資料搬運而非直連**：在 IDMZ 放置資料代理（Data Broker）或歷史資料庫副本。IT 側只能讀取 IDMZ 的副本，不能直接查詢 OT 側的伺服器。
3. **跳板主機（Jump Host）**：遠端維護必須先登入 IDMZ 的跳板主機，經過身份驗證和行為錄影後，才能存取 OT 設備。
4. **禁止主動外連**：OT 區設備不應主動對外發起連線（除非用到雲端服務，但需走專用加密通道）。

### 融合網路 vs 隔離網路

| 面向 | 融合網路（Converged） | 隔離網路（Segregated） |
|------|---------------------|---------------------|
| 定義 | OT 和 IT 共用同一套乙太網基礎架構，靠 VLAN 和 QoS 隔離 | OT 和 IT 完全獨立的實體網路 |
| 建置成本 | 較低（共用交換器、佈線） | 較高（獨立的交換器、獨立的佈線路徑） |
| 管理複雜度 | 高（需要嚴謹的 VLAN 規劃和交換器設定） | 低（物理隔離天生安全） |
| 資安風險 | 設定錯誤就會全面暴露 | 較低，但仍需管控跨網橋接 |
| 適合場景 | 新建廠房、IT 團隊有 OT 網路經驗 | 關鍵基礎設施、合規要求嚴格、既有分離架構 |
| 老手建議 | 中小型產線可考慮，但 VLAN 設計必須經過資安審查 | 半導體廠、石化廠、電力設施建議維持隔離 |

### 無線在工業環境的定位

| 技術 | 適合場景 | 不適合場景 |
|------|---------|----------|
| 工業 Wi-Fi（802.11ax） | AGV/AMR 通訊、移動式 HMI、非關鍵監控 | 閉迴路控制、高可靠度需求 |
| 5G 私網（Private 5G） | 大面積覆蓋、高密度設備、AR 遠端協作 | 預算有限、設備少的小產線 |
| LoRaWAN | 環境監測、資產追蹤、低頻率數據回傳 | 即時控制、高頻數據採集 |
| WirelessHART / ISA100.11a | 程序工業的感測器網路、石化/電廠 | 離散製造的快速控制需求 |

**老手觀點**：無線在工業環境是「最後一哩的補充手段」，不是取代有線的方案。任何與安全相關的迴路一律走有線。無線的最大敵人不是頻寬，而是可靠度和延遲的不確定性。

## 邊緣-霧-雲架構選型

### 什麼時候資料該留在邊緣？

這不是技術偏好問題——是物理約束和業務需求決定的。

| 判斷維度 | 留在邊緣 | 送到雲端 |
|---------|---------|---------|
| 延遲要求 | < 100ms 回應時間 | > 1s 可接受 |
| 資料量 | 高頻時序資料（kHz 級），頻寬不足以全量上傳 | 匯總後的統計值、事件紀錄 |
| 連線可靠度 | 斷線時仍需運作 | 穩定的網路連線 |
| 資料主權 | 法規要求資料留在廠區（如中國資安法、GDPR） | 無跨境限制 |
| 計算需求 | 推論（Inference）、即時異常偵測 | 模型訓練、大規模回溯分析 |
| 設備壽命 | 邊緣設備需配合 OT 週期（10-20 年） | 雲端服務可彈性升級 |

### 架構分層模式

```
┌─────────────────────────────────────────────┐
│  雲端（Cloud）                                │
│  模型訓練、歷史分析、跨廠區彙整、Dashboard      │
├─────────────────────────────────────────────┤
│  霧層（Fog / On-Prem Server）                 │
│  廠級資料整合、模型部署管理、Historian           │
├─────────────────────────────────────────────┤
│  邊緣（Edge）                                 │
│  資料擷取、協定轉換、即時推論、本地緩存           │
├─────────────────────────────────────────────┤
│  現場（Field）                                │
│  感測器、致動器、PLC、DCS                       │
└─────────────────────────────────────────────┘
```

### 邊緣硬體選型考量

| 考量 | 說明 |
|------|------|
| 運算等級 | 純協定轉換用低階閘道器即可；跑 AI 推論需要有 GPU/NPU 的邊緣伺服器 |
| 環境條件 | 無風扇設計、寬溫範圍（-20°C ~ 60°C）、抗振動（IEC 60068-2-6） |
| 作業系統週期 | 工業級 Linux（如 Ubuntu Core、Yocto）需提供至少 10 年安全更新 |
| 管理方式 | 數十台以上必須有遠端部署和更新機制（如容器化 + GitOps） |
| 冗餘設計 | 關鍵製程：雙機熱備、看門狗（Watchdog）、自動回復 |

### 棕地現實檢查（Brownfield Reality Check）

多數工廠不是綠地（Greenfield）新建，而是在既有系統上逐步演進。棕地架構的原則：

1. **先接再改**：用邊緣閘道器（Edge Gateway）側接（Side-car）既有控制器，擷取資料而不修改控制邏輯。這是風險最低的第一步。
2. **雙軌運行**：新系統和舊系統並行一段時間。絕對不要一次切換。
3. **資料品質先行**：在做任何 AI 或分析之前，先確認資料的完整性、時間戳一致性、工程單位是否正確。垃圾進、垃圾出。
4. **選擇可逆的技術**：優先用可逆性高的方案（加一台閘道器 vs 更換整套控制器）。不可逆的決策留到有充分驗證之後。
5. **從一條產線開始**：不要試圖一次改造全廠。選一條代表性產線做概念驗證（PoC），累積經驗後再橫向展開。

## 統一命名空間

### 什麼是統一命名空間？

統一命名空間（Unified Namespace, UNS）是一種事件驅動的資料架構，將工廠所有的資料——從感測器到 ERP——發布到一個共享的、階層化的命名空間裡。任何需要資料的系統直接訂閱，不需要建立點對點的連線。

核心理念：**資料不再「屬於」某個系統——資料屬於企業，任何有權限的系統都可以消費。**

### 為什麼傳統的點對點整合撐不住？

假設一座工廠有 5 個系統需要互相交換資料：

- 點對點需要 5×4/2 = **10 條** 介面
- 再加一個系統變成 6×5/2 = **15 條** 介面
- 每條介面都要個別維護、個別除錯

UNS 模式下，每個系統只需要 **1 條** 連線（連到中央代理），新增系統的邊際成本趨近於零。

### 用 MQTT 實作 UNS

MQTT 是實作 UNS 最常見的協定。主題（Topic）階層結構建議遵循 ISA-95 的語義：

```
{企業}/{廠區}/{區域}/{產線}/{設備}/{資料點}
```

範例：
```
acme/taoyuan-p2/ww-area/line-3/pump-101/flow_rate
acme/taoyuan-p2/ww-area/line-3/pump-101/status
acme/taoyuan-p2/quality/spc/cpk_daily
acme/taoyuan-p2/_meta/heartbeat
```

### Sparkplug B 規範

Sparkplug B（現為 Eclipse 基金會標準）在 MQTT 之上加了三個關鍵機制：

| 機制 | 說明 | 為什麼重要 |
|------|------|----------|
| 出生/死亡憑證（Birth/Death Certificate） | 節點上線時發布出生訊息，離線時代理自動發布死亡訊息 | 系統層面的設備健康狀態可見性，不需要額外的心跳輪詢 |
| 指標定義（Metric Definition） | 每個資料點帶有資料型態、工程單位、時間戳 | 消費端不需要查對照表就能正確解讀資料 |
| 指令（CMD）主題 | 允許從應用端對邊緣節點下指令 | 雙向通訊，不只是單向採集 |

### UNS 常見錯誤

| 錯誤 | 為什麼會出問題 | 正確做法 |
|------|-------------|---------|
| 扁平化的主題結構（所有資料點都在同一層） | 無法做主題層級的訂閱過濾，消費端收到大量不需要的資料 | 遵循 ISA-95 語義的階層結構 |
| 在主題裡放時間戳或動態值 | 主題數量會無限增長，代理負擔過重 | 時間戳放在訊息酬載（Payload）裡，不放在主題路徑裡 |
| 不使用 Sparkplug B 的出生/死亡機制 | 無法區分「設備沒有新資料」和「設備已斷線」 | 啟用出生/死亡憑證，或自行實作心跳機制 |
| 單一代理無冗餘 | MQTT 代理是單點故障，掛掉就全廠斷訊 | 用叢集模式（如 HiveMQ、EMQX 叢集）或至少做主備切換 |
| 忽略權限控制 | 任何能連上代理的用戶端都能讀寫所有主題 | 建立主題層級的存取控制清單（ACL），最小權限原則 |
| 把 UNS 當作歷史資料庫用 | MQTT 代理的保留訊息不是為了長期儲存設計的 | UNS 負責即時資料分發，歷史儲存交給時序資料庫 |

### UNS 與 OPC UA 的關係

UNS 和 OPC UA 不是非此即彼的選擇。常見的共存模式：

- **邊緣側用 OPC UA** 從 PLC/DCS 讀取資料（OPC UA 的資訊模型和設備整合能力強）
- **廠級/企業級用 MQTT/Sparkplug B** 做統一命名空間的資料分發（MQTT 的多對多訂閱模型適合大規模消費）
- 邊緣閘道器負責 OPC UA → Sparkplug B 的轉換

詳見 [protocols-integration.md](protocols-integration.md) 的 OPC UA 和 MQTT 章節。

## 數位孿生

### 三種數位孿生，價值差異極大

ISO 23247 定義了數位孿生（Digital Twin）的架構框架。但在投資之前，先區分你需要的是哪一種：

| 類型 | 描述 | 價值 | 投資規模 | 適合場景 |
|------|------|------|---------|---------|
| 資產孿生（Asset Twin） | 單一設備的數位鏡像：即時狀態、維護紀錄、效能指標 | 預測性維護、剩餘壽命估計 | 中（感測器 + 模型 + 可視化） | 關鍵旋轉設備（泵浦、壓縮機、電機） |
| 製程孿生（Process Twin） | 整段製程的模擬模型：物料平衡、能量平衡、品質預測 | 製程最佳化、異常預警、操作員培訓 | 高（需要製程模型 + 歷史數據 + 校準） | 連續製程（化工、煉油、水處理） |
| 系統孿生（System Twin） | 整座工廠或供應鏈的端對端模擬 | 產能規劃、瓶頸分析、情境模擬（What-if） | 極高（多領域模型整合 + 即時資料驅動） | 新廠規劃、大規模擴產決策 |

### 什麼時候數位孿生是真的有用？

**值得投資的信號**：

1. 設備故障的成本極高（每次停機損失 > 百萬元），預測性維護的回報明確
2. 製程具有物理/化學模型可以建構（不是純黑箱），且有足夠的歷史數據校準
3. 操作員培訓成本高或風險高（如核電、半導體），需要虛擬環境練習
4. 需要頻繁做「如果...會怎樣？」（What-if）分析來支持決策

**過度工程的信號**：

1. 沒有明確的業務問題要解決，只是「數位轉型要有數位孿生」
2. 基礎資料都還不齊全（感測器不夠、資料品質差），就想建孿生
3. 設備不複雜、停機影響可控——一張 Excel 維護排程就夠了
4. 供應商展示的酷炫 3D 模型沒有即時數據驅動——那不是數位孿生，是 3D 動畫

### 數位孿生的技術堆疊

```
┌────────────────────────────────────────────┐
│  應用層（Application）                       │
│  可視化、What-if 模擬、決策支援               │
├────────────────────────────────────────────┤
│  模型層（Model）                             │
│  物理模型、統計模型、混合模型（PINN）           │
├────────────────────────────────────────────┤
│  資料層（Data）                              │
│  UNS、時序資料庫、資產資料模型                  │
├────────────────────────────────────────────┤
│  連接層（Connectivity）                      │
│  OPC UA、MQTT、邊緣閘道器                     │
├────────────────────────────────────────────┤
│  物理層（Physical）                          │
│  感測器、致動器、控制器                        │
└────────────────────────────────────────────┘
```

### 落地建議

1. **從資產孿生開始**：選一台關鍵設備（如主要泵浦或壓縮機），建立振動/溫度/電流的即時監控和劣化趨勢預測。投資小、回報可量化。
2. **不要跳過資料基礎**：數位孿生的品質 = 模型品質 × 資料品質。兩者都低的時候，孿生就是垃圾。
3. **用物理資訊神經網路（PINN）降低資料需求**：純數據驅動模型需要大量標記數據；把已知的物理方程式（質量/能量守恆）嵌入模型，可以用更少的數據達到相同精度。
4. **校準是持續的工作**：模型建好不是結束。設備老化、操作條件變化、原料批次差異都會讓模型漂移（Model Drift）。必須設計持續校準機制。

## 系統整合模式

### 三種基本模式

| 模式 | 特性 | 適用場景 | 風險 |
|------|------|---------|------|
| 點對點（Point-to-Point） | A 直接呼叫 B 的介面 | 系統少（≤ 3 個）、介面穩定、短期方案 | 系統數增加後介面爆炸、維護噩夢 |
| 中介軟體/整合匯流排（Middleware / ESB） | 所有系統透過中央匯流排交換資料 | 企業級整合、複雜轉換規則、需要交易保證 | 匯流排成為單點故障和效能瓶頸 |
| 事件驅動（Event-Driven / Pub-Sub） | 系統發布事件，感興趣的系統訂閱 | 高擴展性、即時性需求、微服務架構 | 事件順序保證、除錯追蹤較困難 |

### 棕地 vs 綠地的整合策略

**綠地（新建）**：

- 首選事件驅動架構（搭配 UNS 概念）
- 從第一天就定義統一的資料模型和命名規範
- 選用支援標準 API 的系統，避免私有協定

**棕地（既有系統改造）**：

- 第一步：**不要改既有系統的介面**。用閘道器或轉接器把既有資料「側抄」出來
- 第二步：建立一個「資料整合層」，可以是 MQTT 代理或輕量級的 Kafka 叢集
- 第三步：新功能（如 AI 模型、Dashboard）只連接整合層，不直接連既有系統
- 第四步：隨著既有系統汰換，逐步把新系統也接到整合層

### 資料模型對齊比協定轉換重要十倍

協定轉換（如 Modbus → OPC UA）是技術問題，通常有現成工具可以解決。但**資料語義的對齊**是業務問題：

- 系統 A 的「流量」單位是 m³/h，系統 B 是 GPM——哪個是對的？
- 系統 A 的「設備狀態」有 5 種代碼，系統 B 有 12 種——怎麼對應？
- 系統 A 用 UTC 時間，系統 B 用本地時間——時間戳差 8 小時

**建議**：在專案早期就建立一份「資料字典」（Data Dictionary），定義每個資料點的名稱、單位、精度、更新頻率、資料來源。這份字典比任何技術架構圖都重要。

## 選型決策框架

### 評估維度

評估任何工業系統或平台時，用這七個維度做結構化的比較：

| 維度 | 評估問題 | 加權建議 |
|------|---------|---------|
| 功能契合度 | 是否能滿足核心需求？客製化程度？ | 高（30%） |
| 整合能力 | 支援哪些協定和標準？開放 API？ | 高（20%） |
| 供應商生態 | 市佔率、合作夥伴、社群活躍度？ | 中（15%） |
| 技術鎖定風險 | 資料可攜性？能否更換供應商？ | 中（15%） |
| 總持有成本（TCO） | 授權費 + 建置 + 維護 + 訓練 + 升級 | 高（10%） |
| 在地支援 | 是否有本地技術支援和系統整合商？ | 中（5%） |
| 長期路線圖 | 供應商的產品方向與你的策略是否一致？ | 低（5%） |

### TCO 計算容易遺漏的項目

| 常被忽略的成本 | 說明 |
|-------------|------|
| 系統整合費用 | 通常是軟體授權費的 2-5 倍 |
| 資料遷移 | 從舊系統搬到新系統的資料清洗和驗證工作 |
| 人員培訓 | 操作員、維護人員、IT 團隊的訓練時間和效率損失 |
| 停機成本 | 系統切換期間的產能損失 |
| 客製化維護 | 客製功能的後續升級相容性問題 |
| 第三方連接器 | 與既有系統的介面開發，常被低估 |

### 技術鎖定風險評估

| 鎖定類型 | 風險等級判斷 | 降低風險的策略 |
|---------|-----------|-------------|
| 資料格式鎖定 | 資料能否以開放格式匯出？ | 要求供應商提供完整的資料匯出 API |
| 通訊協定鎖定 | 是否使用私有協定？ | 優先選用支援 OPC UA / MQTT 的方案 |
| 雲端鎖定 | 是否綁定特定雲端平台？ | 用容器化部署，保持跨雲可攜性 |
| 人才鎖定 | 是否需要稀缺的專業技能？ | 選用有廣泛社群支援的技術 |
| 合約鎖定 | 長期合約的退出條款？ | 在合約中明確資料擁有權和退出條件 |

## 常見踩坑

### 架構設計階段

| 踩坑 | 表面看起來合理 | 為什麼會失敗 | 怎麼避免 |
|------|-------------|-----------|---------|
| 一次全面上雲 | 「雲端彈性大、成本低」 | OT 斷線時工廠停擺；延遲無法滿足即時控制 | 先邊緣後雲端，關鍵控制留在本地 |
| 直接用 IT 架構套 OT | 「都是乙太網，用同一套就好」 | OT 需要確定性、長生命週期、無法隨時重啟 | OT 有自己的設計原則，見 IEC 62443 |
| 選最先進的技術 | 「用最新的一定最好」 | 工業環境需要穩定、長壽的技術，不需要最新 | 技術成熟度比先進性重要，看產業採用度 |
| 架構文件畫完就放著 | 「圖畫好了，開工吧」 | 沒有持續維護的架構圖很快就跟現實脫節 | 架構即程式碼（Architecture as Code），隨變更更新 |

### 整合階段

| 踩坑 | 表面看起來合理 | 為什麼會失敗 | 怎麼避免 |
|------|-------------|-----------|---------|
| 低估 MES 客製化工作量 | 「MES 廠商說開箱即用」 | 每家工廠的流程都不一樣，客製化比例通常 60-80% | 預算至少乘以 2 倍，時程至少乘以 1.5 倍 |
| 忽略時間戳同步 | 「都用伺服器時間就好」 | PLC 的時間可能跟 MES 差好幾秒，事件順序錯亂 | 全廠部署 NTP/PTP 同步，精度要求依應用而定 |
| 假設資料品質是好的 | 「感測器都有在跑，資料應該沒問題」 | 感測器飄移、訊號接地不良、單位標註錯誤比你想的常見 | 先做 2-4 週的資料品質稽核，再決定架構 |
| 沒有考慮退場機制 | 「先上了再說」 | 整合做到一半發現不可行，但已經改了既有系統回不去了 | 每個階段都要有回退計畫（Rollback Plan） |

### 營運階段

| 踩坑 | 表面看起來合理 | 為什麼會失敗 | 怎麼避免 |
|------|-------------|-----------|---------|
| 沒有版本控制 PLC 程式 | 「PLC 跑得好好的不要動」 | 有人偷改了程式沒記錄，下次出問題時無法追溯 | PLC 程式納入版本控制，詳見 [devops-hmi.md](devops-hmi.md) |
| MQTT 代理沒做冗餘 | 「它很穩很少掛」 | 單點故障，掛掉時全廠資料中斷 | 最少主備架構，關鍵場景用叢集 |
| 邊緣設備不做生命週期管理 | 「裝好就不管了」 | 安全漏洞累積、作業系統到期、硬體老化 | 建立邊緣設備的資產清冊和更新排程 |
| 監控只看「有沒有活著」 | 「ping 得通就沒問題」 | 設備活著但資料品質已劣化、效能已下降 | 深度健康指標：資料完整率、延遲分佈、訊息佇列深度 |
